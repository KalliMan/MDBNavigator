# 0.7e Connections module

## 1. Goal

Everything about connecting becomes one module, `src/Modules/Connections`, with three projects: `Contracts` (what other modules may use), `Core` (the rules) and `Infrastructure` (cache, guard, SQLite, encryption). It takes over connect, reconnect and disconnect, the connection guard, the connection cache, the failed-connect wait, and saved connections with their remembered passwords, which leave the accounts project and get their own database context. The static helpers that took services as parameters become injected classes. `MDBNavigator.Domain` is empty afterwards and is removed.

Roadmap step **0.7e** ([ROADMAP.md](../ROADMAP.md), "0.7 Modular structure"). One deliberate behavior change, described in section 2 (account deletion is no longer one transaction). Everything else is unchanged: the same endpoints, status codes, JSON and hub messages. The smoke tests of 0.7b must pass without any change to them.

Docs it changes: `README.md` ("Repository layout"), `docs/specs/authentication.md` (the sentence on deleting an account), `docs/ROADMAP.md` (plan link), the owner's local `CLAUDE.md` (the migrations command).

## 2. Decisions

- **Three projects, as in What2Eat:** `MDBNavigator.Connections.Contracts`, `.Core` (folders `Domain/` and `Application/<use case>/`, root namespace `MDBNavigator.Connections`) and `.Infrastructure`.
- **What other modules get (`Contracts`):** `IDatabaseConnector` (open a database for a session's connection), `IConnectionClosedListener` (be told when a connection is closed), and the three connection exceptions. Nothing else of the module is visible to the workbench code.
- **Saved connections get their own `ConnectionsDbContext`**, in the same SQLite file, with its own migrations history table. The `saved_connections` table is **not** recreated and no data moves:
  - The accounts context gets a migration that only removes the table from its model (its `Up` and `Down` are empty).
  - The connections context gets a first migration that only records the model (empty too), because the table already exists: on an existing database from before, and on a new database from the accounts context's two older migrations, which run first.
  - Nothing has to be done by hand to an existing database, the owner's included. Squashing both histories into one clean initial migration each is possible any time before the first public release, and is the owner's call.
- **Deleting an account is no longer one transaction.** The accounts code no longer reaches into `saved_connections`. Instead every module implements `IUserDataEraser` (in the SharedKernel, like What2Eat's `IPersonalDataEraser`), and account deletion calls them all, then deletes the account. The order is erase first: if deleting the account then fails, the account is still there without its saved connections, which is safe; the other order could leave a deleted user's data behind. The cached connections and running queries, which the endpoint cleared after the deletion until now, are cleared by erasers too.
- **Disconnect tells listeners instead of calling the query registry.** Connections must not know the workbench. `DisconnectCommandHandler` calls every `IConnectionClosedListener`; the one that cancels running queries lives with the registry.
- **The static helpers become classes:** `DbConnectionHelper` becomes `ConnectionOpener` (the connect attempt with its limits) and `DatabaseConnector` (opening a database, with the guard and the provider choice; it replaces `IDatabaseProviderFactory` and its implementation). `RememberedPassword.ResolveAsync` becomes `RememberedPasswordResolver`; the rules that need no services (`SameTarget`, the two messages) stay static in `RememberedPassword`.
- **The cache takes the session and connection ids**, not a pre-built key string. How the key is built is the cache's own business.
- **`ICaptchaVerifier` moves to the SharedKernel.** Connect needs it and so does the API's register check. The implementations stay where they are until 0.7g.
- **The two failed-connect settings get their own options class**, bound to the same `RateLimiting` section, so the module doesn't depend on the API's rate-limit options. The setting names don't change.
- **The API resolves the app database's connection string once** and hands it to the accounts and the connections registration. Both modules keep tables in that one file; neither should own the setting.
- **Use-case folders lose the `Commands/` and `Queries/` level** (`Application/Connect/`, `Application/SavedConnections/CreateSavedConnection/`, ...). Class names don't change.

### Migrations

Both are generated with the EF Core tools, from `src/MDBNavigator.API`, and then edited by hand. The owner's database must not be touched by this: the design-time factories use `design-time.db`, and no `database update` is run.

1. After `SavedConnections` is removed from `AccountsDbContext`:

   `dotnet ef migrations add MoveSavedConnectionsOut --context AccountsDbContext --project ../MDBNavigator.Infrastructure.Accounts --startup-project . --output-dir Persistence/Migrations/Sqlite`

   The generated `Up` drops the table and `Down` recreates it. Replace both bodies with nothing but this comment (in `Up`; `Down` gets "Nothing to undo: see Up."):

   ```csharp
   // The saved_connections table stays where it is. From here on it belongs to the connections module's own
   // context (ConnectionsDbContext); this migration only takes it out of this context's model.
   ```

   The `.Designer.cs` and the snapshot stay as generated (without the entity).

2. With `ConnectionsDbContext` in place:

   `dotnet ef migrations add AdoptSavedConnections --context ConnectionsDbContext --project ../Modules/Connections/MDBNavigator.Connections.Infrastructure --startup-project . --output-dir Persistence/Migrations`

   The generated `Up` creates the table and its index. Replace both bodies with nothing but this comment (in `Up`; `Down` gets "Nothing to undo: see Up."):

   ```csharp
   // The table already exists: the accounts context's migrations AddSavedConnections and AddSavedConnectionPassword
   // created it, before saved connections had a context of their own, and they still run first on a new database.
   // This migration only records the model, so later changes to the table start from it.
   ```

   The `.Designer.cs` and the snapshot stay as generated. Compare the generated `CreateTable` with the columns of the two old accounts migrations before emptying it: names, types, lengths and the unique index must be the same. If they differ, stop and report.

Delete any `design-time.db` file the tools leave behind.

## 6. Edge cases & don'ts

- **Don't touch the smoke tests** (`tests/MDBNavigator.API.Tests`). `AccountTests.Deleting_an_account_removes_everything_of_it` is the test for the eraser path, and it reads `saved_connections` by name: the table name and its columns must not change.
- **Never run `dotnet ef database update`, and never point the tools or a test at `src/MDBNavigator.API/data/mdbnavigator.db`.** The only thing that may open the owner's database is the one start of the API in section 8, which applies the two empty migrations. Before that start, copy the three database files (`mdbnavigator.db`, `-wal`, `-shm`) to the scratch folder as a backup and say where it is.
- **Messages and status codes stay word for word**: "Not Connected! Please reconnect.", "Connection failed: ...", "Reconnection failed: ...", the too-many-attempts and CAPTCHA texts, "Saved connection not found.", the conflict texts.
- **The connect attempt still counts failures exactly as today**: every failure except a cancelled request, for connect and reconnect, and a successful connect does not reset the count.
- **`DatabaseConnector` is the only place that calls a provider's `ConnectAsync`**, so the guard runs on every open. Don't add a second path.
- **Core must not reference Infrastructure types**, EF Core, ASP.NET Core or `Microsoft.Extensions.Caching`. If a moved file needs one of them, it belongs in Infrastructure.
- **`MDBNavigator.Application` may use only `Connections.Contracts`**, never `Connections.Core`. If a workbench file needs a type that is in Core, stop and ask.
- **Lifetimes:** cache, guard and limiter stay singletons; `DatabaseConnector`, `ConnectionOpener`, `RememberedPasswordResolver`, the store and `ConnectionsUserData` are scoped; `RunningQueriesCleanup` is a singleton like the registry. `AccountManagement` (scoped) may take the erasers as `IEnumerable<IUserDataEraser>`.
- **`ExecuteQueryHandler` runs in the queue's own scope**: resolve `IDatabaseConnector` from `services` there, not from the request's scope.
- **Two `DbContext`s, one file:** each `SaveChanges` is its own transaction; don't try to share one. SQLite takes one writer at a time, which both contexts already handle through EF's defaults.
- **The old migrations of the accounts context are not edited**, and their `.Designer.cs` files keep naming `MDBNavigator.Domain.Entities.SavedConnection` as a string. That is history; it compiles.
- **Don't change setting names** (`RateLimiting:FailedConnectsBeforeWait`, `ConnectionCache:...`, `ConnectionGuard:...`, `SavedConnections:PasswordKey`, `ConnectionStrings:AppDb`).
- **No emails or user ids in the new log lines.**
- **Delete `bin/` and `obj/` of a project before `git mv`ing files out of a project that is being removed**, and remove `src/MDBNavigator.Domain` only when `git ls-files src/MDBNavigator.Domain` shows nothing but the project file.
- **Don't rename `MDBNavigator.Infrastructure.Accounts` or move the CAPTCHA code yet** (0.7g), and don't move workbench code (0.7f).
