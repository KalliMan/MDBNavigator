# 2.1 EXPLAIN plan viewer

## 1. Goal

From a query tab, show the plan PostgreSQL uses for one statement, as an indented tree that marks the expensive steps. **Explain** (F7) only plans the statement. **Explain Analyze** (Shift+F7) runs it inside a transaction that is rolled back, and adds real times, rows and buffers.

Roadmap: Phase 2, "EXPLAIN plan viewer" ([ROADMAP.md](../ROADMAP.md)), numbered **2.1** by this step. Docs it changes: README "Features"; `docs/api.md` "Streaming query results"; `docs/security.md` (a new section, "Explain Analyze"); `docs/ROADMAP.md`.

## 2. Decisions

Made with the owner on 2026-11-21. The owner picked the recommended option in each of these four:
- **Explain and Explain Analyze both, and ANALYZE is always rolled back.** The server runs `BEGIN`, then the `EXPLAIN ANALYZE`, then `ROLLBACK`, on the run's own connection. When the statement may change data, the UI asks before running. A rollback can't undo everything: sequence values stay used, and so does anything done outside the database. The confirmation says so.
- **Indented tree.** One row per plan step, with expand and collapse, and a details panel for the selected step. There is no graph view and no new library.
- **What counts as "expensive":**
  - **A step's own share of the total:** time with ANALYZE, cost without. The children's part is subtracted. 30 % or more is high, 10 % or more is medium.
  - **A misestimate badge:** shown where PostgreSQL's row estimate was off by 10× or more, in either direction.
- **The EXPLAIN statement is built on the server.** The run request gets a `plan` option, and the PostgreSQL provider builds `EXPLAIN (...)` and checks there is exactly one statement. The plan comes back through the normal stream as a result set with one JSON cell.

My own choices inside those decisions, listed for the owner:
- **What gets explained:** the editor's selection, or the whole editor when nothing is selected. Run keeps its current behavior and always runs the whole editor.
- **The provider contract** gets a second method, `IQueryRunner.StreamPlan`, instead of more parameters on `StreamQuery`. The plan's text is the provider's own format, PostgreSQL's EXPLAIN JSON. The UI's parser reads that format; a later MS SQL provider would bring its own parser.
- **Options:**
  - Explain: `EXPLAIN (FORMAT JSON)`.
  - Explain Analyze: `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`.
  - No `VERBOSE`, `SETTINGS` or `WAL`. They make the details panel long and add little here.
- **A plan larger than `QueryExecution:MaxRowBytes` is refused with a message** instead of being cut, because a cut JSON can't be read. On the demo that limit is 1 MB, far more than a plan of the sample database needs.
- **The confirmation for Analyze** is based on a check in the UI. Outside comments and quoted text, does the text contain `insert`, `update`, `delete` or `merge` as a word? A wrong "yes" only costs one click; a wrong "no" is still rolled back.
- **The view:**
  - **One "Plan" tab** in the result strip, with a **Tree | JSON** switch like Table | CSV, and a **Copy JSON** button.
  - **The JSON view** reuses `ResultCsvView`, the read-only Monaco editor for plain text.
  - **The status bar** says "Explaining..." or "Running EXPLAIN ANALYZE..." while the run is going.
- **Own time** is `Actual Total Time × Actual Loops`, minus the same for each child, never below 0. For parallel plans the times of the workers add up, so shares there are approximate. The UI doesn't hide that; it is how most plan viewers do it.
- **No new provider-specific code in Workbench.Core.** It only chooses between `StreamQuery` and `StreamPlan`.

### 5.2 PostgreSQL

`PostgresExplain.cs`:
```csharp
namespace MDBNavigator.Providers.PostgreSQL
{
    // The EXPLAIN statement for a plan request.
    internal static class PostgresExplain
    {
        public const string NoStatementMessage = "There is no statement to explain.";
        public const string SeveralStatementsMessage = "Explain works on one statement at a time. Select the statement you want to explain.";
        public const string AlreadyExplainMessage = "This is already an EXPLAIN statement. Remove EXPLAIN to see its plan here, or use Run.";

        // Text: the statement to send. Line: the statement's line in the script, for StatementStarted.
        public static (string Text, int Line) Build(string script, bool analyze) { ... }
    }
}
```

`Build`:
1. `var statements = PostgresScriptSplitter.Split(script);`
2. Throw `InvalidScriptException` when there are 0 statements (`NoStatementMessage`) or more than 1 (`SeveralStatementsMessage`). A script of only comments has 0.
3. If `statements[0].LeadingWords` starts with `"EXPLAIN"`, throw with `AlreadyExplainMessage`.
4. Return `($"EXPLAIN ({(analyze ? "ANALYZE, BUFFERS, " : "")}FORMAT JSON)\n{statement.Text}", statement.Line)`.

The line break is on purpose: the statement's text may start with a `--` comment, which would otherwise swallow the rest of the line. The splitter has already dropped the ending semicolon.

`PostgresQueryRunner.StreamPlan`:
```csharp
public async IAsyncEnumerable<QueryStreamItem> StreamPlan(string script, bool analyze, int? commandTimeoutSeconds = null,
    int? maxRowBytes = null, [EnumeratorCancellation] CancellationToken ct = default)
{
    var (text, line) = PostgresExplain.Build(script, analyze);
    yield return new StatementStarted { StatementIndex = 0, StatementCount = 1, Line = line };

    var plan = await ReadPlanAsync(text, analyze, commandTimeoutSeconds, maxRowBytes, ct);
    yield return new QueryBatch
    {
        ResultSetIndex = 0, IsFirstBatch = true, IsLastBatch = true, BatchIndex = 0,
        Columns = [new ColumnInfo("QUERY PLAN", DbTypeCategory.Json, "json")],
        Rows = [[plan]]
    };
}
```

`ReadPlanAsync` (private):
- When `analyze`, send `BEGIN` first, on the same connection, through an `NpgsqlBatch` with one command, as `StreamQuery` does.
- Run the EXPLAIN text the same way (timeout as in `StreamQuery`) with `CommandBehavior.SequentialAccess`, and read one row.
- Before reading the value, take its size with `reader.GetBytes(0, 0, null, 0, 0)`. When `maxRowBytes` is set and the size is larger, throw:
  `new InvalidScriptException($"The plan is {CutCellText.Size(size)}, more than this server's limit of {CutCellText.Size(maxRowBytes.Value)} per row (QueryExecution:MaxRowBytes).")`
- Otherwise read it with `await reader.GetFieldValueAsync<string>(0, ct)` and return it.
- In a `finally`, when `analyze`: try `ROLLBACK` with `CancellationToken.None`, and catch and ignore any exception from it, with a comment saying why. The run's connection is closed when the run ends, and closing it rolls back an open transaction too. So a failed `ROLLBACK`, after a cancel or a broken connection, leaves nothing behind. Dispose the reader before the `ROLLBACK`.
- Don't touch `stats`. `StreamPlan` has no stats parameter, so the status bar shows only the time.

### 5.6 `features/queryPlan/queryPlan.ts` (pure, tested)

```ts
import { CellValue } from '../../models/databaseCommand/result/cellValue';

export const HIGH_SHARE = 0.3;
export const MEDIUM_SHARE = 0.1;
// Rows expected against rows got, either way, from which a step is marked.
export const MISESTIMATE_FACTOR = 10;

export type ShareLevel = 'high' | 'medium' | null;

export interface PlanNode {
  // Path from the root: "0", "0.1", "0.1.0". Unique within a plan, and stable for the same plan.
  id: string;
  depth: number;
  label: string;                 // planNodeLabel
  // "SubPlan 1", "InitPlan 2", "CTE films": EXPLAIN's "Subplan Name"; null when absent.
  subplanName: string | null;
  estimatedRows: number;         // "Plan Rows" (per loop)
  actualRows: number | null;     // "Actual Rows" (per loop); null without ANALYZE
  loops: number | null;          // "Actual Loops"; null without ANALYZE
  neverExecuted: boolean;        // ANALYZE and Actual Loops = 0
  totalCost: number;             // "Total Cost"
  ownCost: number;               // Total Cost minus the children's Total Cost, at least 0
  totalMs: number | null;        // Actual Total Time × Actual Loops; null without ANALYZE
  ownMs: number | null;          // totalMs minus the children's totalMs, at least 0
  share: number;                 // 0..1: ownMs (ANALYZE) or ownCost, divided by the sum over all steps
  level: ShareLevel;             // share >= HIGH_SHARE: 'high', >= MEDIUM_SHARE: 'medium'
  // PostgreSQL expected far fewer ('under') or far more ('over') rows than it got. ANALYZE only, not for steps never run.
  misestimate: { factor: number; direction: 'under' | 'over' } | null;
  // The step's own properties as EXPLAIN gave them, in its order, without "Plans", formatted (formatPlanValue).
  details: [string, string][];
  children: PlanNode[];
}

export interface PlanTrigger { name: string; relation: string | null; ms: number; calls: number }

export interface ParsedPlan {
  analyzed: boolean;
  root: PlanNode;
  planningMs: number | null;     // "Planning Time"
  executionMs: number | null;    // "Execution Time"
  totalCost: number;             // the root's Total Cost
  triggers: PlanTrigger[];       // "Triggers" (ANALYZE of a statement that fired triggers); [] otherwise
  // The plan as EXPLAIN gave it, indented with 2 spaces: the JSON view and Copy JSON.
  json: string;
}

export type PlanParseResult = { plan: ParsedPlan } | { error: string };

export function parsePlan(cell: CellValue): PlanParseResult;
export function planNodeLabel(node: Record<string, unknown>): string;
export function formatPlanValue(value: unknown): string;
// The rows on screen: depth-first, children of collapsed steps left out.
export function visiblePlanRows(root: PlanNode, collapsed: ReadonlySet<string>): PlanNode[];
// What a key does in the tree (see the rules below). null: the key isn't handled.
export function planKeyAction(
  rows: PlanNode[], selectedId: string, key: string, collapsed: ReadonlySet<string>
): { selectedId: string; collapsed: ReadonlySet<string> } | null;
// True when the SQL may change data: insert, update, delete or merge as a word outside comments and quoted text.
export function mayChangeData(sql: string): boolean;
```

**`parsePlan` rules:**
- The cell is the JSON as a string; parse it with `JSON.parse`. An array, already parsed, is accepted too. Anything else, or a parse failure, gives `{ error: 'The plan couldn\'t be read: <reason>' }`.
- The top level must be an array whose `[0]` is an object with a `Plan` object. Otherwise the error is `The plan couldn't be read: unexpected format.`
- `analyzed` is true when `[0]` has `Execution Time`, or the root plan has `Actual Loops`.
- `json` is `JSON.stringify(top, null, 2)`.
- Build the nodes recursively, depth from 0, ids as paths. Missing numbers count as 0.
- `ownMs` and `ownCost` subtract the children's totals and are never below 0. A step that was never executed has `totalMs` 0.
- `share` is divided by the sum of `ownMs` over all steps (with ANALYZE), or of `ownCost` (without). When the sum is 0, every share is 0.
- `misestimate`, for ANALYZE and steps that ran: `est = Plan Rows`, `act = Actual Rows`, `hi = max(est, act)`, `lo = max(min(est, act), 1)`, `factor = hi / lo`.
  - When `factor >= MISESTIMATE_FACTOR`, it is `{ factor: Math.round(factor), direction: act > est ? 'under' : 'over' }`. Otherwise it is null.
  - `under` means PostgreSQL expected fewer rows than it got.
- `triggers` come from `[0].Triggers` (`Trigger Name`, `Relation`, `Time`, `Calls`).

**`planNodeLabel` rules,** as PostgreSQL's text EXPLAIN writes them:
- **The base** is `Node Type`.
- **`Aggregate`:**
  - The base comes from `Strategy`: `Sorted` gives `GroupAggregate`, `Hashed` gives `HashAggregate`, `Mixed` gives `MixedAggregate`, and `Plain` or none gives `Aggregate`.
  - `Partial Mode` `Partial` or `Finalize` goes in front: `Partial HashAggregate`.
- **`SetOp`:** with `Strategy` `Hashed` it becomes `HashSetOp`.
- **`Parallel Aware: true`** puts `Parallel ` in front: `Parallel Seq Scan`.
- **Joins:** `Nested Loop`, `Hash Join` and `Merge Join` with a `Join Type` other than `Inner` name it.
  - `Nested Loop` with `Left` gives `Nested Loop Left Join`.
  - `Hash Join` with `Anti` gives `Hash Anti Join`.
  - `Merge Join` with `Full` gives `Merge Full Join`.
  - Two-word types such as `Right Anti` are written as they come.
- **Index scans:**
  - `Index Scan` and `Index Only Scan` add ` Backward` when `Scan Direction` is `Backward`, then ` using <Index Name>`.
  - `Bitmap Index Scan` adds ` on <Index Name>`.
- **What the step works on:**
  - With `Relation Name`, add ` on <Relation Name>`, then ` <Alias>` when the alias differs from the relation name.
  - Otherwise `CTE Name` gives ` on <CTE Name>`, and `Function Name` gives ` on <Function Name>`. Add ` <Alias>` when it differs.
  - Otherwise, `Subquery Scan` and `Values Scan` add ` on <Alias>` when there is one.
- **Test cases:** `Seq Scan on film f`, `Index Scan using film_pkey on film`, `Index Scan Backward using idx on t`, `Bitmap Heap Scan on rental r`, `Bitmap Index Scan on idx_fk_customer_id`, `Hash Join`, `Hash Left Join`, `Nested Loop Anti Join`, `HashAggregate`, `Finalize GroupAggregate`, `Parallel Seq Scan on payment p`, `CTE Scan on x`, `Function Scan on generate_series g`, `Sort`, `Limit`.

**`formatPlanValue`:**
- Numbers use `toLocaleString('en-US', { maximumFractionDigits: 3 })`.
- Booleans become `yes` or `no`.
- Strings stay as they are.
- Arrays are joined with `, `, each item formatted the same way, and objects inside them go through `JSON.stringify`.
- Objects use `JSON.stringify`, and null is an empty string.

**`planKeyAction`:**
- `ArrowDown` and `ArrowUp` select the next or previous visible row, and stay put at the ends.
- `Home` and `End` select the first and last row.
- `ArrowRight` on a step with children expands it if it is collapsed; otherwise it selects its first child. On a leaf it does nothing, but still returns the same values: the key is handled.
- `ArrowLeft` on an expanded step with children collapses it; otherwise it selects its parent (the id without its last `.n`). The root stays.
- Any other key returns null.

**`mayChangeData`:**
- First remove the comments (`--` to the end of the line, and `/* … */`), single-quoted strings with `''` doubled inside them, double-quoted identifiers, and dollar-quoted text (`$tag$…$tag$`).
- Then test `/\b(insert|update|delete|merge)\b/i`.
- Test cases:
  - `update t set a=1` → true
  - `select 'delete'` → false
  - `-- delete\nselect 1` → false
  - `select "update" from t` → false

**`docs/api.md`**, after the `POST /api/databaseCommand` example in step 2:
> Add `"plan": "Estimate"` or `"plan": "Analyze"` to get the plan of one statement instead of running the script. The provider puts `EXPLAIN (FORMAT JSON)` (or `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`) in front of it. With `Analyze` the statement really runs, inside a transaction that is rolled back. The run then sends one `StatementStarted` and one result set: a single batch with one column `QUERY PLAN` (category `Json`) and one row, whose value is EXPLAIN's JSON as a string. A script that isn't exactly one statement, an `EXPLAIN` statement, or a plan larger than `MaxRowBytes` ends with `CommandFinished` `Failed` and a message. An unknown `plan` value is a `400`.

**`docs/security.md`**, a new section after "Connection credentials":
> ## Explain Analyze
>
> `EXPLAIN ANALYZE` measures a statement by running it. The server always runs it inside a transaction and rolls the transaction back, and the UI asks first when the statement may change data. A rollback undoes the statement's changes to the data, but not everything: sequence values stay used, and anything done outside the database (`dblink`, a function that writes files or sends messages) stays done. It is an ordinary run otherwise: the same run limits, rate limits and database permissions apply, so on the public demo it can only read.

## 6. Edge cases & don'ts

- **Never run `EXPLAIN ANALYZE` outside `BEGIN … ROLLBACK`,** and never send `COMMIT`. Don't build the three statements into one script for `StreamQuery`: the splitter would make them three statements, with wrong indexes and three `StatementStarted` messages.
- **Don't put PostgreSQL syntax in the UI or in Workbench.Core.** The `EXPLAIN` text exists only in `PostgresExplain`.
- **Don't change Run.** It still runs the whole editor, not the selection.
- **No new npm or NuGet packages,** and no graph library.
- **`QueryPlanMode` lives in Workbench.Core,** not in `Providers.Abstractions`. The provider only gets `bool analyze`. Don't add a project reference; the architecture tests must pass unchanged.
- **An unknown `plan` must not be accepted as `None` silently.** The DTO's converter makes a bad string a 400. A number outside the enum is caught by the validator.
- **The cancel and run-time limit still work during a plan.** `ReadPlanAsync` passes `ct` to every call except the `ROLLBACK`.
- **The demo:** `demo_reader` may `BEGIN`, `EXPLAIN` and `ROLLBACK`. `statement_timeout` still applies. Don't add any demo-only branch.
- **Never-executed steps** (`Actual Loops` 0) show `never executed`, have no misestimate, and count 0 in the shares.
- **A plan with one step** (`select 1`) shows one row with a 100 % share, or 0 % when its own cost or time is 0. Don't divide by zero.
- **A huge plan** (thousands of steps) needs no virtualization in this step. Note it under "Changed while building" if it is visibly slow with the API test's 20,000-value plan.
- **Lint:** zero warnings, no `any` (use `unknown` and narrow), and `react-hooks` rules hold. `planKeyAction` returns a new `Set` when `collapsed` changes, never a mutated one.
- **Keep `JsonCellValue.cs` and `cellValue.ts` unchanged.** The plan is a plain string cell.

## Changed while building

- **`Analyze_rolls_back_what_the_statement_changed`** counts with `select count(*)::int`, not `count(*)`: `count(*)` is a bigint, which arrives as the string `"0"` (JsonCellValue), so the plan's "the row is `[0]`" needed the cast.
- **`ModifyTable` steps** (INSERT, UPDATE, DELETE, MERGE) are labelled `ModifyTable on actor`, because the plan's label rules don't cover them. PostgreSQL's text EXPLAIN writes `Update on actor` (from the step's `Operation`). Fixed after review (last item).
- **`QueryPlanView`** mounts the JSON editor only while the Plan tab is in front (`isActive`), the tree always. The plan said both stay mounted; the tree was the one that needed to keep its scroll position, and this avoids a hidden Monaco editor.
- **`PlanTree.onKey`** returns a boolean (handled or not), so the tree can call `preventDefault`.
- **Browser check** used the built UI served from the scratch API (no second Vite on 3100), as in the earlier steps' notes, and a throwaway `postgres:17-alpine` container with a small Pagila-like schema. With only 200 rows in `actor`, PostgreSQL plans `actor_id = 1` as a Seq Scan, not `Index Scan using actor_pkey`.
- **Large plans:** the 20,000-value plan of the limits test is refused by the server, so the UI never meets it; a plan of thousands of steps was not tried.
- (Reviewer, after building) `ModifyTable` steps are labelled as PostgreSQL's text EXPLAIN does, from `Operation`: `Update on actor`, `Insert on film f`. The share format is one function, `formatShare` in `queryPlan.ts`, used by both the tree and the details panel, so a small share reads `<1 %` in both.
