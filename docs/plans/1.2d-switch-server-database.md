# 1.2d Switch server or database

## 1. Goal

The server and database labels in a query tab's query bar become menus. Picking another connected server or another database changes where the tab's SQL runs. The editor text stays, nothing runs by itself, and the status bar says where the results on screen came from.

Roadmap step 1.2d (`docs/ROADMAP.md`). It is the last step of 1.2 and is built on the same branch (`1.2-saved-connections`, which the owner merges once 1.2a–1.2d are done). **UI only: no backend change**, because `POST api/databaseCommand/execute` already takes `connectionId` and `databaseName` with every run. Changes these README sections: root README "Features" (the theme/color bullet) and the UI README ("Layout" `src/ui` row, "How a query runs in the UI"). Mock agreed with the owner: https://claude.ai/artifact/Gw31LspYk3AyPELCvR9Acu (boards "Main" and "Other states").

**Before starting:** `git log --oneline -3` must show the 1.2c commit ("Saved connections: remember password (roadmap 1.2c)"), and `git status` must be clean apart from this plan. Otherwise stop and ask the owner.

## 2. Decisions

Agreed with the owner on 2026-11-13, after looking at the mock:

1. **The server menu lists only connected servers.** Saved connections aren't listed, because connecting from inside a menu would need the password, CAPTCHA and error handling the connect dialog already has. A footer item, **"Connect to another server…"**, opens that dialog (`connectNewDatabase()`). Connecting there does **not** move the tab to the new server; the user then picks it from the menu.
2. **The database menu shows the list the tree already loaded** (`DatabaseSchemaContext`; the provider loads it right after connecting). While it is loading the menu says "Loading databases…". If loading failed, the menu shows the error and a **Retry** button (`fetchDatabases`). Opening the menu doesn't load anything by itself.
3. **Database after a server switch:** the same database name if the new server has it (exact, case-sensitive match). Otherwise that connection's default database (`connectedResult.databaseName`) if the server has it, otherwise the first database in the list. When the name changes this way, a **note** replaces the address on the right of the query bar, in the warning color: `"sales" isn't on Reporting, so the tab now uses "reports".` If the new server's list hasn't loaded (still loading or failed), the tab takes the connection's default database, or keeps its current name when there is no default. When that changes the name, the note says `Reporting's database list isn't loaded, so the tab uses its default database "reports".` The note clears when either menu opens, on the next switch, and on Run.
4. **While the tab's query runs, both menus are disabled.** The tooltip says "Stop the query to change where it runs".
5. **A tab whose server was disconnected** keeps its SQL. Its server menu still works: the old server is listed first, greyed out and not pickable, with a "disconnected" tag, and the connected servers follow. Its database menu is disabled ("Pick a connected server first"). The message on the right reads "Disconnected. Pick a connected server to run this query." When no server is connected at all, it reads "Disconnected. Connect to a server to run this query." (the footer item still opens the dialog).
6. **Switching never runs anything** (tabs opened with "Select Top 100" included), and **the old results stay** until the next run replaces them.
7. **The status bar says where the results came from**, after a run that completed or was cancelled: "Results from Local PG · sales" (muted). When the tab's target has changed since that run: "Results are from Local PG · sales. Run to refresh." (warning color).
8. **The tab follows its target:** its second line (server · database), its color stripe and its tooltip all change with it.
9. **The database menu has a filter box** (case-insensitive substring), and the connection's default database has a small **"default"** tag.
10. **Our own dropdown, no library** (no Radix, Headless UI or downshift; 1.2 decided against Radix). It follows the WAI-ARIA "select-only listbox" pattern: arrows, Home/End, Enter or Space to pick, Esc to close, the focus back on the button. It renders in a portal like the context menu (`ui/contextMenu/Menus.tsx`), so the editor and the splitter can't clip it.

Deviation from the mock, on purpose: the server menu's heading is "Servers" rather than "Connected servers", because a disconnected server's tab lists its old server in the same list.

### What we found in the code (and why the plan is shaped this way)

- **The tab's query object must not change.** `DatabaseCommand` copies `databaseCommandQuery.cmdQuery` into the editor whenever the query object changes (`useEffect(..., [databaseCommandQuery])`), so putting the new target into that object would throw away the user's edits. The target therefore lives next to it, in `MainBar`'s `TabData.target`, and every run sends the target's connection and database.
- **`DatabaseCommand.query` in the command reducer is never set.** Nothing dispatches `Queried`. So where a run ran is recorded in a new field, `ranOn`, set by the `Executing` action. `query` and `Queried` stay as they are (not this step's cleanup).
- **A failed database list never reached its connection.** The schema reducer puts a `Databases`-scope error on the global `error` (which nothing shows) when the list hasn't arrived yet, and no action marks one connection as loading. The plan adds `DatabasesLoading` and keeps that error on the connection's schema, so the menu can show "loading" and "failed" correctly. The tree doesn't read `schema.error`, so it is unaffected (check: `grep -rn "\.error" src/features/databaseTreeView` finds no `schema.error`).
- **Freeing results on disconnect** (in `MainBar`) has to look at the connection the results came from (`ranOn`), not the tab's current target, because those differ after a switch.

### 5.4 `features/databaseCommand/queryTargets.ts` (new)

```ts
import { DatabaseServerConnection } from '../../contexts/databaseServerConnect/DatabaseServerConnectReducer';
import { DatabaseSchema } from '../../contexts/databaseSchema/DatabaseSchemaReducer';
import { QueryTarget } from '../../models/databaseCommand/query/queryTarget';
import { connectionAddress, UNKNOWN_CONNECTION_COLOR } from '../../utils/connectionColor';

// Helpers for a query tab's target (1.2d). Pure, so they can get unit tests in 0.3a.

export function findConnection(connections: DatabaseServerConnection[], connectionId: string): DatabaseServerConnection | undefined {
  return connections.find(c => c.connectedResult?.connectionId === connectionId);
}

export function queryTargetFor(connectionId: string, databaseName: string, connections: DatabaseServerConnection[]): QueryTarget {
  const match = findConnection(connections, connectionId);
  const connection = match?.connectedResult;
  if (!match || !connection) {
    return { connectionId, serverName: 'Unknown server', databaseName, address: '', color: UNKNOWN_CONNECTION_COLOR };
  }
  return { connectionId, serverName: match.name, databaseName, address: connectionAddress(connection), color: match.color };
}

export type DatabaseList =
  | { state: 'loaded'; names: string[] }
  | { state: 'loading' }
  | { state: 'failed'; message: string };

// A loaded list wins over an error: a failed refresh keeps the list it had.
export function databaseList(schema: DatabaseSchema | undefined): DatabaseList {
  if (schema?.databasesDetails) {
    return { state: 'loaded', names: schema.databasesDetails.databases.map(d => d.name) };
  }
  if (schema?.error) {
    return { state: 'failed', message: schema.error };
  }
  return { state: 'loading' };
}

export interface DatabaseChoice {
  databaseName: string;
  // Shown in the query bar when the database changed without the user picking it.
  note: string | null;
}

// The database a tab uses after switching to another server: the same name when that server has it, else the
// connection's default database, else the server's first database.
export function databaseForServer(
  currentDatabase: string,
  serverName: string,
  list: DatabaseList,
  defaultDatabase: string | null | undefined,
): DatabaseChoice {
  if (list.state !== 'loaded') {
    const databaseName = defaultDatabase || currentDatabase;
    return {
      databaseName,
      note: databaseName === currentDatabase
        ? null
        : `${serverName}'s database list isn't loaded, so the tab uses its default database "${databaseName}".`,
    };
  }
  if (list.names.includes(currentDatabase)) {
    return { databaseName: currentDatabase, note: null };
  }
  const fallback = defaultDatabase && list.names.includes(defaultDatabase) ? defaultDatabase : list.names[0];
  if (!fallback) {
    return { databaseName: currentDatabase, note: null };
  }
  return { databaseName: fallback, note: `"${currentDatabase}" isn't on ${serverName}, so the tab now uses "${fallback}".` };
}
```

### 5.6 `ui/dropdown/Dropdown.tsx` (new)

A button that opens a listbox menu. It knows nothing about servers. Write it like this:

```tsx
import { ReactNode, useCallback, useEffect, useId, useLayoutEffect, useRef, useState } from 'react';
import { createPortal } from 'react-dom';
import { LuCheck, LuChevronDown, LuSearch } from 'react-icons/lu';

export interface DropdownOption {
  key: string;
  // The row's content; the check mark for the selected option is added after it.
  content: ReactNode;
  // What the filter box matches (case-insensitive substring).
  filterText?: string;
  selected?: boolean;
  disabled?: boolean;
}

interface Props {
  // The button's content (a color square or icon plus the current value). A chevron is added after it.
  label: ReactNode;
  // Names the button and the list for screen readers, e.g. "Server".
  ariaLabel: string;
  // The button's tooltip; shown on a wrapper, because a disabled button shows none in some browsers.
  title?: string;
  disabled?: boolean;
  // The small uppercase heading at the top of the menu.
  heading: string;
  options: DropdownOption[];
  onSelect: (key: string) => void;
  // Set: a filter box above the options, with this placeholder.
  filterPlaceholder?: string;
  // Set: shown instead of the filter box and the options (loading, an error with Retry).
  status?: ReactNode;
  // Below the options, after a separator, such as "Connect to another server…". It gets a function that closes the menu.
  footer?: (close: () => void) => ReactNode;
  onOpenChange?: (open: boolean) => void;
  // The menu's minimum width in px.
  minWidth?: number;
}
```

Behavior (every point is required):

- **State:** `open`, `filter`, `activeKey` (the highlighted option), `position` (`{ left, top }` in page px). Refs: `triggerRef` (button), `menuRef` (portal root), `filterRef` (input), and `onOpenChangeRef` kept up to date in an effect with no deps (the `latest` pattern), so `close` can be a `useCallback` with `[]` deps.
- **Visible options:** with `filterPlaceholder` set and a non-blank filter, the options whose `filterText` contains the trimmed filter, ignoring case; otherwise all of them. `enabled` = the visible ones that aren't disabled. The highlighted option is computed during render: `activeKey` if it is in `enabled`, else the first of `enabled`, else none. No effect resets it, so typing in the filter never leaves the highlight on a hidden row.
- **Opening** (button click while closed, or ArrowDown on the button): read the button's `getBoundingClientRect()`, set `position = { left: rect.left + window.scrollX, top: rect.bottom + window.scrollY + 4 }`, clear the filter, set `activeKey` to the selected enabled option (else the first enabled one), set `open`, call `onOpenChange(true)`. A click while open closes it. All of this happens in event handlers, never in effects.
- **Focus:** an effect on `[open]` focuses the filter input when there is one and `status` is unset, else the list (`tabIndex={0}` on the `<ul>` in that case, `-1` otherwise).
- **Closing**, `close(returnFocus: boolean)`: `setOpen(false)`, `onOpenChangeRef.current?.(false)`, and focus the button when `returnFocus`. It closes:
  - on Esc (focus back on the button),
  - after picking an option (focus back on the button, then `onSelect(key)`),
  - on a `mousedown` anywhere outside both the menu and the button (a document listener added while open; clicks on the button are left to its own click handler, which toggles),
  - when focus moves outside the menu and the button (`onBlur` on the menu root: close only when `relatedTarget` is set and is outside both; a `null` `relatedTarget` is a click, which the `mousedown` listener already handles),
  - on window `resize` (the stored position would be stale).
- **Clicks inside the menu keep the focus where it is:** `onMouseDown` on the menu root calls `preventDefault()` unless the target is the input. Without this, clicking an option would blur the list and close the menu before the click arrives.
- **Keys** (an `onKeyDown` on the menu root):
  - ArrowDown/ArrowUp move the highlight through `enabled`, wrapping around (from no highlight, Down goes to the first, Up to the last).
  - Home/End go to the first/last, except while typing in the input.
  - Enter picks the highlighted option (or the only enabled one), except when the event comes from a `<button>` (a footer or Retry button handles its own Enter).
  - Space picks too, but only when the list itself has focus.
  - Esc closes.
  - Call `preventDefault()` for every key that is handled. Tab is left alone.
- **Scrolling:** an effect on `[open, highlighted key]` calls `scrollIntoView({ block: 'nearest' })` on the highlighted option.
- **Right edge:** a `useLayoutEffect` on `[open, position]` measures the menu. If its right edge is past `window.innerWidth - 8`, it sets `menuRef.current.style.left` to `max(8, left - overflow)`. That writes the DOM, not state, so the lint rule against state updates in effects isn't triggered.
- **Markup:**
  - **Button:** wrapped in `<span className="flex" title={title}>`. It is `type="button"`, `aria-haspopup="listbox"`, `aria-expanded={open}`, and starts with `<span className="sr-only">{ariaLabel}: </span>`, then `label`, then `<LuChevronDown size={12} className="opacity-70" aria-hidden="true" />`. Classes: `flex h-7 items-center gap-1.5 rounded-[3px] border px-2 cursor-pointer hover:bg-hover disabled:cursor-not-allowed disabled:border-line-subtle disabled:text-fg-faint disabled:hover:bg-transparent`, plus `border-accent bg-selected text-on-selected` while open, else `border-line text-fg`.
  - **Menu:** `createPortal(..., document.body)`, root `absolute z-40 rounded border border-line bg-canvas py-1 shadow-lg`, `style={{ left, top, minWidth }}`.
  - **Heading:** `px-3 pb-1 pt-1.5 text-[11px] font-semibold uppercase tracking-wide text-fg-muted`.
  - **Filter**, when `filterPlaceholder` is set and `status` isn't: a `<label>` with `mx-2 mb-1.5 mt-1 flex h-7 items-center gap-1.5 rounded-[3px] border border-line bg-surface px-2 focus-within:border-accent`, holding `<LuSearch size={13} className="text-fg-faint" aria-hidden="true" />`, `<span className="sr-only">Filter</span>` and the `<input>`. The input is `type="text"`, `role="combobox"`, `aria-expanded="true"`, `aria-controls={listId}`, `aria-autocomplete="list"`, `aria-activedescendant` = the highlighted option's id, with classes `min-w-0 flex-1 bg-transparent text-fg outline-none placeholder:text-fg-faint`.
  - **`status`**, when set: `<div className="px-3 py-1.5">{status}</div>` instead of the filter and the list.
  - **List:** `<ul id={listId} role="listbox" aria-label={ariaLabel} className="max-h-72 overflow-y-auto outline-none">`, with `aria-activedescendant` when the list itself has focus (no filter).
  - **Options:** each one is `<li id={`${listId}-${index}`} role="option" aria-selected={!!o.selected} aria-disabled={o.disabled || undefined}>`. Use the index in the id, because keys are database names that may hold any character. Classes: `flex items-center gap-2 px-3 py-1.5`, plus:
    - disabled: `cursor-default text-fg-muted`;
    - selected: `cursor-pointer bg-selected text-on-selected`, plus `ring-1 ring-inset ring-accent` when it is also highlighted;
    - highlighted only: `cursor-pointer bg-hover`.

    `onMouseEnter` highlights an enabled option, and `onClick` picks it. Inside: `<span className="min-w-0 flex-1">{o.content}</span>` and, when selected, `<LuCheck size={14} aria-hidden="true" />`.
  - **No visible options:** with a filter typed, `<li role="presentation" className="px-3 py-1.5 text-xs text-fg-muted">No match for "{filter}".</li>`.
  - **Footer:** `<div className="my-1 h-px bg-line-subtle" />` and then `footer(() => close(true))`.
- `listId` comes from `useId()`.

## 6. Edge cases & don'ts

- **Don't put the target into `databaseCommandQuery`** (or replace `TabData.databaseCommandQuery`): the editor would be reset to the original SQL.
- **Don't use `DatabaseCommand.query` or dispatch `Queried`** for this; use `ranOn`. Don't remove them either (not this step).
- **Don't run anything on a switch**, and don't clear the results on a switch.
- **Don't add a dependency** (no Radix, Headless UI, downshift, floating-ui).
- **Don't fetch databases when a menu opens.** The provider loads them on connect; only Retry fetches.
- **Don't move the tab when "Connect to another server…" succeeds.**
- **Picking the current server or database** does nothing (no note, no state change).
- **The current server is the only connected one:** the server menu shows it (selected) and the footer. That's fine.
- **A server is reconnected** (tree context menu): `Reconnected` keeps the connection id, name and color, so tabs pointing at it keep working. Nothing to do.
- **The tab's server disconnects while a menu is open:** the menus re-render from context. The open server menu then shows the disconnected row. The database menu's button becomes disabled, but a menu that is already open stays usable until it closes. Accepted.
- **Closing or hiding the tab while a menu is open:** a click on another tab is an outside `mousedown`, so it closes. Unmounting removes the portal.
- **Database names are case-sensitive** in PostgreSQL. Compare exactly, and filter ignoring case only.
- **The empty key `''`** is the disconnected row. It is disabled, so `onSelect` never gets it, but the handler ignores unknown keys anyway.
- **Ctrl+Enter** in the editor must run on the current target: it goes through `latest.current`, which now includes `target`.
- **No `dark:` variants or palette classes.** The tags use `border-danger`/`border-line`, not red/grey palette names.
- **Lint has zero warnings:** no state updates inside effects (the Dropdown only writes `style.left` there), no `!` where a type guard is easy, exhaustive deps (use the refs described).
