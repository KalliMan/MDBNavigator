# 1.2b Saved connections: connect dialog

## 1. Goal

The connect dialog gets a list of the user's saved connections on the left (from the 1.2a API). Picking one fills the form, the user types the password and connects. A "Save this connection" checkbox saves a new entry, or the changes to the selected one, when the connect succeeds. A saved entry can be deleted from the dialog, and its color is chosen with a color picker. A connection's optional default database is used when connecting and is expanded in the tree. A connection opened from the form shows its name in the tree and on its query tabs.

Roadmap step 1.2b (`docs/ROADMAP.md`). Builds on 1.2a, on the same branch (`1.2-saved-connections`, merged when 1.2a–1.2d are all done). Changes these README sections: "Features" and "API" (the `connect` row). UI README: "Source layout". `CLAUDE.md`: the "Values kept in sync" list. Decisions agreed with the owner on 2026-11-13.

**Before starting:** `git log --oneline -3` must show the 1.2a commit ("Saved connections: storage and API (roadmap 1.2a)"), and `git status` must be clean apart from this plan. Otherwise stop and ask the owner.

## 2. Decisions

Agreed with the owner on 2026-11-13:

- **Layout: the list on the left, the form on the right.** The left pane has "New connection" at the top, then the saved entries, each showing a color square, the name, and `user@host:port` below it in muted text. Picking one fills the form. The dialog opens with "New connection" selected and nothing chosen automatically, so it behaves the same every time.
- **Saving happens on connect, through a checkbox. There is no separate Save button.**
  - The label is "Save this connection" when "New connection" is selected, and "Save changes" when a saved entry is selected.
  - It starts **unticked** for "New connection" and **ticked** for a saved entry, so edits to a saved entry are kept by default.
  - The save runs only **after a successful connect**: POST for a new entry, PUT for the selected one. A failed connect saves nothing.
  - **Consequence, accepted:** changing a saved entry (rename, new color, other port) needs a successful connect. Deleting doesn't.
- **The default database is used on connect.** `databaseName` becomes an optional field of connect and reconnect, so this step has a small backend part. The server opens that database whenever a request names none: the connect test and the database list. Today that is PostgreSQL's default, a database named like the user, which fails on hosted servers where a user may only open their own database. After connecting, that database is expanded in the tree (once, when its node first appears; the user's own expand/collapse wins afterwards).
- **The shown name:** the tree's server node, the query tab's second line and the query bar's server chip show the name from the form. When the name is empty, the server name is shown, as today. The query bar still shows `user@host:port` on the right, so the real target stays visible.

Settled in 1.2a, or by this plan:

- **Own components only** (`ModalWindow`, `Input`, `Select`, `Button`); no Radix or shadcn, and no new dependencies.
- **Color picker:** seven swatches. "Automatic" (null, the hashed color, with a dashed border) comes first, then the six `CONNECTION_COLORS`. The picked color is the connection's color while it is open. With "Automatic", `pickConnectionColor` picks a color as today. A chosen color is used even when another open connection has the same one: the user asked for it.
- **The name and color fields are always shown**, also when the checkbox is unticked: they set the connection's shown name and color even without saving.
- **The name is needed only to save.** With the checkbox ticked and no name, Connect is disabled and a hint says "Give it a name to save it."
- **Checks before connecting, only when saving:** an empty name, a name over 100 characters, a name already used by another entry (ignoring case), a full list when saving a new entry (100), and the port (1–65535). They give the same messages as the server. When one fails, the dialog shows it and doesn't connect, so a typo can't cost a connect attempt (failed connects count towards the wait). The server stays the authority: if it still answers 400 or 409, apiAgent shows its toast, and the connection that just opened stays open.
- **The list loads every time the dialog opens** (`GET /api/savedConnections`); at most 100 rows, so there is no cache and no context. If loading fails, the pane says "Couldn't load saved connections." and the form still works (apiAgent also shows its toast).
- **Delete** applies to the selected entry and asks first, inside the form: "Delete "X"? This doesn't close open connections." with Delete and Cancel. There is no `window.confirm`. Deleting doesn't touch open connections: their name and color stay until they are closed.
- **After a successful save** the dialog is already gone (connecting closes it), so a toast confirms: `Saved "Local dev".`
- **Switching entries clears the password.** Passwords belong to one server; 1.2c may remember them.
- **The reconnect dialog doesn't show the saved list, the name, the color or the checkbox.** It shows the database field, filled from the connection. Reconnect keeps the connection's shown name and color, as it keeps the color today.
- **The default database is not part of the color hash** (`serverName:port:userName`, unchanged), so colors stay the same as before.
- **`.env.development.local` still fills the "New connection" form** in dev mode. There is no new variable for the database.

### 5.7 `features/connect/savedConnectionForm.ts`

Pure functions, no React.

```ts
// What the dialog edits. Same fields as a saved connection plus the password; port as typed.
export interface ConnectForm {
  name: string;
  serverType: ServerType;
  serverName: string;
  port: number;
  databaseName: string;
  userName: string;
  password: string;
  color: string | null;
}

// "New connection": dev defaults from .env.development.local, as today, and empty name, database and color.
export function newConnectForm(): ConnectForm

// A saved entry in the form; password empty (typed each time).
export function formFromSaved(saved: SavedConnection): ConnectForm

// The reconnect dialog: everything from the open connection, password empty.
export function formFromConnected(connected: ConnectedResult): ConnectForm

// What connect/reconnect send: databaseName trimmed, empty → null; serverName and userName as typed (the server trims nothing today; keep it so).
export function toConnectionSettings(form: ConnectForm): ConnectionSettings

// What POST/PUT send: name, serverName, userName and databaseName trimmed; empty database → null.
export function toSavedInput(form: ConnectForm): SavedConnectionInput

export function toDisplay(form: ConnectForm): ConnectionDisplay  // name trimmed, empty → null; color as is

// The first problem that would make the save fail, or null. Only called when the checkbox is ticked.
// selectedId: the entry being changed (it may keep its own name), null for a new one.
export function saveProblem(form: ConnectForm, saved: SavedConnection[], selectedId: string | null): string | null
```

`saveProblem` checks, in this order, with these messages (the server's own, so the user sees one wording):
1. name empty after trim → `Name is required.`
2. trimmed length > `SAVED_CONNECTION_NAME_MAX_LENGTH` → `Name must be at most 100 characters.`
3. another entry (id ≠ selectedId) has the same `name.trim().toUpperCase()` → `A saved connection named "<trimmed name>" already exists.`
4. `selectedId === null && saved.length >= SAVED_CONNECTIONS_MAX` → `You can save up to 100 connections. Delete one first.`
5. port not an integer from 1 to 65535 → `Port must be between 1 and 65535.`

Build messages 2 and 4 from the constants.

### 5.11 `ConnectToServer.tsx`

Props:

```ts
interface Props {
  // Reconnect: the open connection; the dialog then shows no saved list, name, color or checkbox.
  initialConnection?: ConnectedResult | null;
  // The connect dialog: the saved list, name, color and the save checkbox.
  allowSaved?: boolean;
```

Layout with `allowSaved`: `flex` with `SavedConnectionList` on the left and the form (`pl-4 pr-4 pb-2`, as today) on the right. Without it, only the form, as today.

Form rows, in order (each `mb-8`, as today):
1. Name (`allowSaved` only): `Input` with `maxLength={SAVED_CONNECTION_NAME_MAX_LENGTH}`, placeholder "Needed only to save it".
2. Server Type, Server Name, Port: as today.
3. Database: `Input` type text, placeholder "Optional: the user's default", `maxLength={128}`.
4. User Name, Password: as today.
5. Color (`allowSaved` only): `ConnectionColorPicker` with `autoColor={autoConnectionColor(toConnectionSettings(form))}`.
6. The checkbox (`allowSaved` only): `<label className="flex items-center gap-2"><input type="checkbox" className="accent-accent" …/> Save this connection | Save changes</label>`. Under it, when ticked with an empty name: `text-sm text-fg-muted` "Give it a name to save it."

Then the error block: `localError ?? error`, the same `role="alert"` markup as today. Then the captcha, as today. Then the buttons: Connect (primary), Delete (secondary, only when a saved entry is selected), Cancel (as today).

Behaviour:
- **Selecting an entry:** `form = formFromSaved(entry)`, `saveChecked = true`, `localError = null`, `confirmingDelete = false`. "New connection": `newConnectForm()`, `saveChecked = false`. The `Input`s are controlled (`initialValue` is their `value`), so they follow the new form.
- **`dataOk`:** as today (server name, user name, password, captcha when required), plus `!saveChecked || form.name.trim()`.
- **Submit:**
  1. As today, return early when `!dataOk || isConnecting`.
  2. When `saveChecked`: `const problem = saveProblem(form, saved, selectedId)`. If there is one, `setLocalError(problem)` and return without connecting.
  3. `setLocalError(null)`. Capture `const input = toSavedInput(form)`, `const id = selectedId` and `const shouldSave = allowSaved && saveChecked` **before** awaiting, because the dialog unmounts on success.
  4. `const ok = await onOk(toConnectionSettings(form), captchaToken, toDisplay(form))`. Reset the captcha as today.
  5. When `ok && shouldSave`: call the module-level function `saveAfterConnect(id, input)`, not a method of the component. It runs `id ? update : create`, then `toast.success(`Saved "${input.name}".`)`. It never sets component state (the component is gone by then). Failures toast through apiAgent; catch and ignore them here, so there is no unhandled rejection.
- **Delete:** the Delete button sets `confirmingDelete = true`. The row then shows, instead of the buttons: `Delete "<name>"? This doesn't close open connections.` with Delete (primary) and Cancel (secondary). Confirm calls `remove(selectedId)`. On true: select "New connection". On false: stay (the toast explains it).
- While `isConnecting`, the list, the checkbox and Delete are disabled.

## 6. Edge cases & don'ts

- **Never send or store a password through `savedConnectionsApi`.** `toSavedInput` has no password field. Don't spread the form into it.
- **Save only after `onOk` resolved true.** Don't save before connecting "to be safe", and don't save on a failed connect.
- **No `setState` after the connect succeeded:** the dialog unmounts when `Connected` is dispatched. Capture what the save needs before `await onOk(...)`, and save in a module-level function.
- **Don't add a Save button or a "save without connecting" path.** The owner chose the checkbox; editing needs a connect.
- **The pre-checks don't replace the server's.** A 409 or 400 after connecting is a toast, and the connection stays open. Don't disconnect it, and don't parse server messages.
- **Don't put the default database into the color hash,** or every existing connection changes color.
- **The database field is sent as `null` when empty,** never `""` (the server treats `""` as none too, but keep the contract clean).
- **Don't change `ConnectionName`** on the server; the UI uses `DatabaseServerConnection.name`.
- **Reconnect never touches saved entries.**
- **Don't fetch the list in a context or on app start**; only the open dialog needs it.
- **Theme tokens only;** no palette classes, no `dark:` (UI README "Conventions").
- **The dialog grows wider (about 56rem).** `ModalWindow` already centers and scrolls, so leave it as it is.
- **No personal data in logs:** the new `DatabaseName` in `PrintMembers` is fine (no secret, and the same kind of data as `ServerName`). Don't log it anywhere new.
- **Don't commit.** Finish with the summary, what was verified, and a commit message.

### A. Backend: the default database (scratch build, port 5199)

Use a throwaway app database and the owner's local PostgreSQL. Connecting is allowed (it is read-only use); credentials are in `mdb-navigator-ui/.env.development.local`. In Git Bash, pass Windows-style paths to the app (`cygpath -m`): a `/c/...` path is read as `C:\c\...` on Windows.

```bash
W=$(cygpath -m "$S")
cd MDBNavigator.API
ASPNETCORE_ENVIRONMENT=Development ASPNETCORE_URLS=http://localhost:5199 \
  ConnectionStrings__AppDb="Data Source=$W/test.db" Auth__Mode=None \
  dotnet "$S/build/MDBNavigator.API.dll"
```

With `C='{"serverType":"PostgreSQL","serverName":"<server>","port":<port>,"userName":"<user>","password":"<password>"'`:

1. `curl -s -H 'id: t1' -H 'Content-Type: application/json' -d "$C,\"databaseName\":\"postgres\"}" http://localhost:5199/api/databaseConnection/connect` → `200`, with `"databaseName":"postgres"`.
2. Same with `"databaseName":"no_such_db_1_2b"` → `400` with PostgreSQL's `database "no_such_db_1_2b" does not exist`. This proves the connect test opens the given database.
3. Without `databaseName` → `200` with `"databaseName":null` (as before 1.2b).
4. With a 129-character `databaseName` → `400`, `DatabaseName must be at most 128 characters.`
5. After step 1, `GET /api/databaseSchema/databases/<connectionId>` → `200` with the list.

Stop the API and delete `$S/test.db*`.

### C. In the browser, the way the owner runs it

Visual Studio's `https` profile with the Vite dev server on 3000. The implementer can't click through the UI, so they give the owner this checklist, and the owner reports back:

1. Sign in. The connect dialog shows "New connection" selected, the form filled from `.env.development.local`, and "No saved connections yet.".

3. Open the dialog again ("+" in the sidebar). "Local dev" is listed with its color and `user@host:port`. Pick it: the form is filled, the password is empty, and the checkbox reads "Save changes" and is ticked.
4. Change the color, type the password, and connect. The new connection has the new color. In the dialog again, the entry shows the new color.
5. New connection, the name "local DEV", ticked → the inline error `A saved connection named "local DEV" already exists.`, and no connect happens.
6. Ticked with an empty name → Connect disabled, with the hint "Give it a name to save it.".
7. A wrong password with the checkbox ticked → the connect error shows, and nothing is saved (the list is unchanged after reopening).
8. Save an entry with Database set to an existing database. On connect, that database is expanded in the tree. Collapse it and reload its tables: it stays collapsed.
9. New Query on a database of "Local dev": the tab's second line and the query bar chip say "Local dev", and the query bar still shows `user@host:port`.
10. Reconnect a connection (tree context menu): no list, no name or color, and the database is filled. After reconnecting, the name and color are unchanged.
11. Delete "Local dev" from the dialog: the confirm text shows, and after Delete the entry is gone and the open connection is unaffected.
12. Both themes (top bar toggle): the list, the swatches and the selected row are readable in light and dark.
13. With `Auth:Mode = None`: the same dialog works, and entries saved there don't appear after switching back to accounts.
