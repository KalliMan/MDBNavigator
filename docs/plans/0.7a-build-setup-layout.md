# 0.7a Build setup and layout

## 1. Goal

Move the backend projects into `src/` and `tests/` under their current names, and give the repository shared build settings: one `Directory.Build.props`, every NuGet version in `Directory.Packages.props`, a pinned SDK, and `MDBNavigator.slnx` instead of `MDBNavigator.sln`. No C# code changes and no behavior change.

Roadmap step **0.7a** ([ROADMAP.md](../ROADMAP.md), "0.7 Modular structure"). It is the base for 0.7b–0.7g, which create the modules.

Docs it changes: `README.md` ("Repository layout", "Running locally", "Production build", "Configuration", the saved-password key command, the `.http` link, "Development"), `mdb-navigator-ui/README.md` (two paths), and the owner's local `CLAUDE.md` (paths and one new convention).

## 2. Decisions

Made with the owner on 2026-11-14, or following from that agreement:

- **All six projects move to `src/` as they are**, same folder names, project names and namespaces. Renames and splits come in 0.7c–0.7g, one module at a time. The test project moves to `tests/`.
- **`mdb-navigator-ui` stays at the repository root.** Many docs and notes name it, and moving it gains nothing.
- **`.slnx` replaces `.sln`.** The following steps add and move projects several times; in `.slnx` that is a one-line edit with no GUIDs. The owner has Visual Studio 2026 (18.11), which opens it.
- **Warnings are errors in Release only**, as in What2Eat: CI builds Release, local Debug builds are not blocked by an unused variable. The solution has 0 warnings in Release today (checked), so nothing needs fixing.
- **One version change only:** `Microsoft.Extensions.DependencyInjection.Abstractions` and `Microsoft.Extensions.Logging.Abstractions` go from 10.0.13 to 10.0.14, the version every other Microsoft package here already uses. No other package is upgraded in this step.
- **The Visual Studio container tooling is removed** from the API project: the `Microsoft.VisualStudio.Azure.Containers.Tools.Targets` package, `DockerDefaultTargetOS`, and the `Container (Dockerfile)` launch profile. They belong to the old Dockerfile, which is broken; 0.4a writes a new one that doesn't need them.
- **The old `Dockerfile`s and `docker-compose.yml` are not touched.** The README already says not to use them, and 0.4a replaces them. Their paths become even more wrong after the move; that is accepted.
- **No `.editorconfig` in this step.** It would add style rules and with them a diff across the whole code base.
- **The whole trial was run in a scratch copy first:** with the files below, `dotnet build MDBNavigator.slnx -c Release` gives 0 warnings and 0 errors, and all 90 tests pass.

## 6. Edge cases & don'ts

- **Visual Studio must be closed and the API stopped before step 2.** Visual Studio holds the `.sln` and locks `bin/`, and the running API has the SQLite database open. If `git mv` fails with "Permission denied", stop and ask the owner to close Visual Studio; don't work around it by copying.
- **The owner's SQLite database must survive the move.** `MDBNavigator.API/data/` is git-ignored and holds their accounts and saved connections. `git mv` renames the whole folder, ignored files included, so it travels along. Check it before and after (section 8). Never delete or recreate the `data` folder.
- **Change `.gitignore` in the same step as the move.** Otherwise `src/MDBNavigator.API/data/` shows up as untracked and could be committed.
- **Use `git mv` for the seven folders**, not copy and delete, so git records renames and history stays readable.
- **Delete `bin/` and `obj/` after the move**, not selectively: the restore files in `obj/` hold absolute paths.
- **Don't rename anything.** `MDBNavigator.API` keeps its capital letters, and no namespace changes. Renames belong to 0.7c–0.7g.
- **Don't upgrade packages** beyond the two named in section 2, even if newer versions exist.
- **Don't add `<TreatWarningsAsErrors>` or other settings to single projects.** If a Release build shows a warning that the trial run did not, stop and report it instead of suppressing it.
- **Don't touch `Dockerfile`, `mdb-navigator-ui/Dockerfile`, `docker-compose.yml` or `.dockerignore`.** They are replaced in 0.4a.
- **Don't change `docs/plans/*`.** Older plans keep the paths that were true when they were written.
- **User secrets are not affected:** they are found through `UserSecretsId`, not the folder.
- **`.vs/` at the root stays.** It is git-ignored; Visual Studio creates new state for the `.slnx` by itself.
- **No C# file changes.** If a build error seems to need one, stop and ask.

## 7. Steps

Each step ends in a state that builds.

**Step 0: before starting**

1. Ask the owner to close Visual Studio and stop the API. Check that nothing is left: `tasklist | grep -iE "devenv|MDBNavigator"` prints nothing.
2. `git status --short` prints nothing.
3. Note the database file's size: `ls -la MDBNavigator.API/data/`.

**Step 1: shared build files, projects still in place**

1. Create `global.json`, `Directory.Build.props` and `Directory.Packages.props`.
2. Apply the `.csproj` rules to all seven project files, including the two extras for the API project. Leave the test project's `<ProjectReference>` for step 2.
3. Remove the `Container (Dockerfile)` profile from `launchSettings.json`.
4. Build: `dotnet build MDBNavigator.sln -c Release`. Expect `0 Warning(s)` and `0 Error(s)`.

**Step 2: the move**

1. Delete the leftover folder `MDBNavigator.Infrastructure/MDBNavigator.Infrastructure.PostgreSQL/`.
2. Delete every `bin/` and `obj/` folder inside the seven project folders.
3. `mkdir src tests`, then `git mv` each of the six projects into `src/` and the test project into `tests/`.
4. Change the test project's `<ProjectReference>`.
5. Change the two `.gitignore` lines.
6. Create `MDBNavigator.slnx` and `git rm MDBNavigator.sln`.
7. Build and test: `dotnet build MDBNavigator.slnx -c Release`, then `dotnet test MDBNavigator.slnx -c Release --no-build`.

**Step 3: docs and comments**

1. `README.md`, `mdb-navigator-ui/README.md`, `CLAUDE.md`.
2. The six frontend comment changes.
3. In `mdb-navigator-ui`: `npm run check`, `npm test`, `npm run build`.

**Step 4: verification** (section 8), then the usual summary, what was verified, and a commit message. Don't commit.

Suggested commit message: `Build setup and layout: src/ and tests/, shared build settings, central package versions (roadmap 0.7a)`
