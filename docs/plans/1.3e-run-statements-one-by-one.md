# 1.3e Run scripts statement by statement

## 1. Goal

The server splits a script at its semicolons and runs the statements one after another on one connection, the way psql, DBeaver and DataGrip do. The row limit then counts per result set, stopping one result no longer loses the rest of the script or undoes its earlier changes, a failing statement is named with its number and line, and the status bar shows which statement is running.

Roadmap step 1.3e (new, added to `docs/ROADMAP.md` by this step). Changes these docs: root `README.md` ("Features", "Configuration", "Streaming query results", a new "How a script runs", "Development"), `mdb-navigator-ui/README.md` ("How a query runs in the UI"), `CLAUDE.md` ("Building and checking").

**Before starting:** `git status --short` shows only `docs/ROADMAP.md` (the 0.6c row) and this plan. `MDBNavigator.Infrastructure.PostgreSQL/PostgreSQLServer.cs` has `StreamQuery` with a `do … while (await reader.NextResultAsync(ct))` loop. Otherwise stop and ask.

## 2. Decisions

### The problem (found 2026-11-14)

- `QueryExecution:MaxRowsPerExecution` is one budget for the whole run. Four `SELECT`s on a table with more than 100,000 rows give one result tab: the first uses the budget, the command is cancelled, and the other three never run.
- Npgsql sends a multi-statement command as one implicit transaction. The cancel at the limit is an error for PostgreSQL, so everything the script did before is rolled back, while the status bar says "Query executed successfully". Checked with a read-only probe: a session setting made by the first statement was gone after the cancel.

### Agreed with the owner on 2026-11-14

1. **Run statements one by one** (option 3 of three), not one command per script.
2. **The first failing statement stops the script.** Earlier results stay.
3. **The splitter lives on the server**, so the API keeps taking one script.
4. **The setting is renamed** to `QueryExecution:MaxRowsPerResultSet`, because its meaning changes. The old key is not read any more (nothing is released yet).
5. **This step comes before the UI polish (1.4a–c).**

### Decided by the planner (reported to the owner)

- **The loop lives in the provider.** Splitting and the stop rule are PostgreSQL knowledge; another provider (MS SQL: `GO` batches) will bring its own. The handler stays database-neutral.
- **Each statement is sent as an `NpgsqlBatch` with one `NpgsqlBatchCommand`.** A batch command's text goes to the server untouched (probed: PostgreSQL itself answers a text with two statements). An `NpgsqlCommand` is searched for semicolons by Npgsql and split again, which would break a function body written as `BEGIN ATOMIC … END`.
- **How a result is stopped at the limit** depends on what is safe (both probed):
  - *Cancel* when the statement only reads and no transaction of the user is open. Immediate, and the next statement runs normally (100 of 100 rounds).
  - *Skip* otherwise: read the remaining rows and throw them away. Cancelling there would abort the user's transaction (`25P02` on the next statement) or undo the statement's own changes (`UPDATE … RETURNING`). Skipping 2,000,000 narrow rows took half a second.
  - When unsure, skip: it is slower and never wrong.
- **`truncated` is exact.** At the limit the server reads one more row: only if there is one, the result is truncated. Today a result with exactly 100,000 rows is called truncated.
- **No total cap per run.** The limit protects the browser from one huge result; a script with many big results is the user's own choice, as in DBeaver.
- **A new hub message, `StatementStarted`,** before each statement. The status bar needs it to say "Executing statement 3 of 5" and, exactly, "Skipping the remaining rows…". Without it a run that is skipping rows looks hung.
- **The UI takes `StatementStarted` through the batch buffer** (the latest per run, at most every 150 ms), so an insert script with thousands of statements doesn't cause thousands of renders.
- **The error text carries the statement** (`Statement 2 of 5 (line 14): …`), only when the script has more than one. Structured fields come with the roadmap's "Error panel and error position".
- **Per-statement messages** (rows affected and timing for each statement) need a Messages panel of their own. It is added to the roadmap's "Later" table, not built here. `recordsAffected` stays one number: the sum.
- **The unused `parameters` argument of `StreamQuery` is removed.** Nothing passes it, and parameters shared by all statements of a script have no meaning.
- **The first backend test project** (xUnit, roadmap 0.3b) starts here, for the splitter and the stop rules: they are pure and easy to get subtly wrong.
- **Not in this step:** a warning when a script ends with a transaction still open (it is rolled back, as today; the README now says so), pipelining statements for speed, psql's backslash commands.

### What we found in the code

- `ExecuteQueryHandler` opens one provider (one connection) per run and disposes it at the end. So a run always starts outside a transaction, and a transaction left open is rolled back when the connection closes.
- `IDatabaseProvider.StreamQuery` is called from the handler only.
- The UI already keys result sets by `resultSetIndex` and allows gaps, shows one tab per result set, and enables sort and filter per result set as soon as its last batch arrived (`isComplete`).
- `reader.RecordsAffected` is `-1` for statements that report no count (`SELECT`, `SET`).
- The solution has an empty "Test" solution folder.

## 5. Contracts

### 5.1 `PostgresScriptSplitter.cs`

```csharp
namespace MDBNavigator.Infrastructure.PostgreSQL
{
    // One statement of a script.
    // Text: as written, from its first character to just before its ending semicolon, trimmed. Comments stay in.
    // Line: 1-based line, in the script, of its first character that is neither white space nor comment.
    // LeadingWords: its first four bare words, upper-cased (fewer when it has fewer).
    // HasDataChangingWord: INSERT, UPDATE, DELETE or MERGE appears in it as a bare word.
    public sealed record ScriptStatement(string Text, int Line, IReadOnlyList<string> LeadingWords, bool HasDataChangingWord);

    public static class PostgresScriptSplitter
    {
        public static IReadOnlyList<ScriptStatement> Split(string script);
    }
}
```

The class comment says that the rules follow psql's own scanner (`psqlscan.l`), and why the split is done here at all (one statement per round trip: see section 2).

One pass over the script, character by character. State per statement: `parenDepth`, `beginDepth`, the leading words, `hasDataChangingWord`, the position and line of the first significant character (none yet = the statement is empty so far). Lines are counted by `\n`, so `\r\n` works. At each position, the first rule that matches:

1. **`--`**: a comment to the end of the line. Not significant.
2. **`/*`**: a block comment. They nest: count `/*` and `*/` until the depth is back to zero. Unterminated: it runs to the end of the script. Not significant.
3. **`'`**: a string. It ends at a `'` that is not followed by another `'` (`''` is a quote inside the string). If the string is an *escape string*, a backslash also takes the next character with it, so `\'` does not end it. A string is an escape string when the bare word directly before the quote, with nothing between, is exactly `E` or `e`. Unterminated: to the end of the script.
4. **`"`**: a quoted identifier. It ends at a `"` not followed by another `"`.
5. **`$`**: a dollar quote, when the text here is `$tag$` with `tag` empty or a letter, underscore or character ≥ U+0080 followed by letters, digits, underscores or characters ≥ U+0080. It ends at the next occurrence of exactly the same `$tag$` (ordinal comparison). Unterminated: to the end of the script. Any other `$` (such as `$1`) is an ordinary character.
6. **An ASCII digit**: skip the whole run of ASCII letters, digits and underscores (`1e5` and `0x1F` are numbers, not words).
7. **A bare word**: starts with an ASCII letter, an underscore or a character ≥ U+0080, and continues with those, digits and `$`. Read it whole (so the `$` in `a$b$c` never reaches rule 5), upper-case it with `ToUpperInvariant`, then:
   - if fewer than four leading words are stored, store it;
   - if it is `INSERT`, `UPDATE`, `DELETE` or `MERGE`, set `hasDataChangingWord`;
   - if the statement is a routine definition and `parenDepth == 0`: `BEGIN` adds 1 to `beginDepth`; `CASE` adds 1 when `beginDepth >= 1`; `END` subtracts 1 when `beginDepth > 0`. A statement is a routine definition when its leading words start with `CREATE FUNCTION`, `CREATE PROCEDURE`, `CREATE OR REPLACE FUNCTION` or `CREATE OR REPLACE PROCEDURE`. (This keeps the semicolons of a `BEGIN ATOMIC … END` body inside the statement; it is psql's heuristic.)
8. **`(`** adds 1 to `parenDepth`; **`)`** subtracts 1 when it is above 0. (`CREATE RULE … DO ALSO (a; b)` has semicolons inside parentheses.)
9. **`;`** with `parenDepth == 0` and `beginDepth == 0`: the statement ends here. Any other `;` is an ordinary character.
10. **White space** is not significant. **Any other character** is ordinary.

Everything matched by rules 3 to 9, and an ordinary character, is significant, except a `;` that ends the statement. When a statement ends (at its semicolon or at the end of the script): if it has a significant character, add it to the result; otherwise drop it (`;;`, a trailing comment). Its text starts at the first character after the previous split that is not white space (a leading comment is part of the text) and is trimmed at the end. Then reset the per-statement state.

### 5.2 `PostgresStatementRules.cs`

```csharp
namespace MDBNavigator.Infrastructure.PostgreSQL
{
    public static class PostgresStatementRules
    {
        // Stopping a statement by cancelling it is an error for PostgreSQL: it undoes what the statement changed
        // and aborts an open transaction. That is harmless only for a statement that just reads, outside a
        // transaction. When in doubt the answer is no, and the caller reads the remaining rows away instead.
        public static bool CanCancelAtRowLimit(ScriptStatement statement, bool inTransaction);

        // Whether a transaction block is open after the statement ran without error.
        public static bool InTransactionAfter(ScriptStatement statement, bool inTransaction);
    }
}
```

- `CanCancelAtRowLimit`: `!inTransaction`, and `!statement.HasDataChangingWord`, and the first leading word is `SELECT`, `TABLE`, `VALUES`, `WITH` or `SHOW`. No leading word: `false`.
- `InTransactionAfter`, by the leading words:
  - none: `inTransaction` unchanged;
  - first is `BEGIN`, or first is `START` and second is `TRANSACTION`: `true`;
  - first is `COMMIT`, `END`, `ROLLBACK` or `ABORT`: unchanged when the leading words contain `TO` (rollback to a savepoint) or `CHAIN` (`COMMIT AND CHAIN` opens the next one), otherwise `false`;
  - anything else: unchanged.
  - A comment says that wrong guesses must land on "open": then a result is skipped where it could have been cancelled, which is only slower.

### 5.5 `PostgreSQLServer.StreamQuery`

Signature as in the interface (`[EnumeratorCancellation]` stays on `ct`). Body:

```csharp
var statements = PostgresScriptSplitter.Split(script);
// The connection was opened for this run, so no transaction is open yet.
var inTransaction = false;

for (var index = 0; index < statements.Count; index++)
{
    var statement = statements[index];
    yield return new StatementStarted { StatementIndex = index, StatementCount = statements.Count, Line = statement.Line };

    // A batch command's text goes to the server untouched. Npgsql searches an NpgsqlCommand's text for
    // semicolons and splits it again, which breaks a function body written as BEGIN ATOMIC ... END.
    await using var batch = new NpgsqlBatch(_connection) { BatchCommands = { new NpgsqlBatchCommand(statement.Text) } };
    if (commandTimeoutSeconds.HasValue)
    {
        batch.Timeout = commandTimeoutSeconds.Value;
    }
    await using var reader = await batch.ExecuteReaderAsync(ct);

    var cancelled = false;
    if (reader.FieldCount > 0)
    {
        // columns: as today
        // rows: as today (JsonCellValue.From, batches of batchSize, stats.RowCount++), with ResultSetIndex = index
        //       and a row count of this result set only.
        // At the limit: limitReached = await reader.ReadAsync(ct); then leave the loop. One more row is read
        //       only to learn whether the result is longer; it is not sent.
        // Then the last batch, always: IsLastBatch = true, Truncated = limitReached,
        //       SkippingRest = limitReached && !canCancel
        //       where canCancel = PostgresStatementRules.CanCancelAtRowLimit(statement, inTransaction).
        // Then, when limitReached: stats.Truncated = true, and
        //       canCancel  -> await StopReaderAsync(batch, reader); cancelled = true;
        //       otherwise  -> while (await reader.ReadAsync(ct)) { }   // the user's Cancel still stops this
    }

    if (!cancelled)
    {
        // The count is known once the reader is past the statement.
        await reader.NextResultAsync(ct);
        if (stats != null && reader.RecordsAffected >= 0)
        {
            stats.RecordsAffected = Math.Max(stats.RecordsAffected, 0) + reader.RecordsAffected;
        }
    }

    inTransaction = PostgresStatementRules.InTransactionAfter(statement, inTransaction);
}
```

- The limit check stays before the "batch is full" check, as today.
- The last batch is yielded before the cancel or the skipping starts, so the browser has the rows and its tab while the server is still busy.
- `StopReaderAsync` takes `(NpgsqlBatch batch, NpgsqlDataReader reader)` and calls `batch.Cancel()`; the rest is unchanged. Its comment stays true.
- The old `parameters` handling and the `do … while (NextResultAsync)` loop go away.
- Comments explain the two ways of stopping and why (section 2).

- `flush()`: clear the timer; dispatch `RowsAppended` when the queue has batches; then dispatch one `StatementStarted` per stored message and empty the store. (The early return for an empty queue has to go: there may be statements only.) Rows first, so a result set is in the state before the statement after it is announced.
- Returns `{ push, pushStatement, flush }`. The file comment says why statements go through the buffer (section 2).

`useDatabaseCommandContext.tsx`: `onStatementStarted(result: StatementStartedResult) { context!.batchBuffer.pushStatement(result); }`, returned with the other handlers. `onCommandFinished` already flushes first.

`useCommandBatchResultNotifications.ts`: a fourth prop `onStatementStarted`, `connection.on("StatementStarted", …)` and the matching `off`. `App.tsx` passes it.

A new section after "Streaming query results" (after the "If the hub drops" paragraph):

> ### How a script runs
>
> The server splits the script into statements at its semicolons and runs them one after another on one connection, opened for the run. This is what psql does.
>
> - **Splitting** follows psql's rules: a semicolon inside a string, a quoted identifier, dollar-quoted text, a comment, parentheses or a `BEGIN ATOMIC … END` function body does not split. psql's backslash commands are not supported.
> - **Each statement commits on its own.** To make several statements all-or-nothing, put them between `BEGIN` and `COMMIT`; a long data script is also much faster that way. A transaction still open when the script ends is rolled back, because the connection is closed.
> - **The first failing statement stops the script.** Earlier statements keep their results and, outside a transaction, their changes.
> - **The row limit counts per result set.** A statement that only reads (`SELECT`, `TABLE`, `VALUES`, `WITH` or `SHOW`, without `INSERT`, `UPDATE`, `DELETE` or `MERGE` in it) and runs outside a transaction is cancelled at the limit, which is immediate. Any other statement is read to its end with the remaining rows thrown away, because cancelling it would undo its changes or abort the open transaction. For a very large result that takes a while; the run can be cancelled as usual.
> - A `SELECT` that calls a function which changes data, and returns more rows than the limit, is cancelled like any other `SELECT`, and the function's changes are undone. Run it between `BEGIN` and `COMMIT` to have it read to the end.
>
> The splitter and these rules are `PostgresScriptSplitter` and `PostgresStatementRules` in the PostgreSQL provider, with unit tests.

## 6. Edge cases & don'ts

- **Don't use `NpgsqlCommand` for the user's statements.** It splits at semicolons again (section 2). The schema queries keep using Dapper as they are.
- **Don't set the `Npgsql.EnableSqlRewriting` switch.** It is global and would break the Dapper queries' named parameters.
- **Don't cancel when `CanCancelAtRowLimit` says no,** not even to be fast. The skip loop is the safe path.
- **Don't wrap the user's statements in a transaction or a cursor.** The script decides about transactions.
- **Don't catch exceptions around the statement loop** (C# forbids `yield` in a `try` with a `catch` anyway). A failing statement's exception leaves the iterator; the handler turns it into `Failed`.
- **An empty script** (only white space, comments or semicolons) has no statements: no messages but `CommandFinished` with `Completed`, `rowCount` 0, `recordsAffected` -1.
- **A statement without columns** sends no batches; its index is skipped, as before.
- **A result set with columns and no rows** still sends one batch that is first and last.
- **A result of exactly `MaxRowsPerResultSet` rows is not truncated.**
- **The user's Cancel while rows are skipped** ends the run as `Cancelled` through the existing path (`ReadAsync(ct)` throws).
- **`RecordsAffected` is not read after a cancel at the limit**: the statement was a read, and the reader is disposed.
- **Thousands of statements** mean thousands of round trips and commits, as with psql. That is accepted; the README says how to make it fast (`BEGIN … COMMIT`).
- **Don't add fields to `CommandFinishedDto`.** The statement is in the error text for now.
- **UI: don't dispatch `StatementStarted` directly** from the hub handler; it goes through `batchBuffer`.
- **UI: theme tokens only** (`text-warning`), no palette classes, no `dark:` variants. Lint has zero warnings; no `as` casts.
- **The owner's PostgreSQL is read-only.** The checks in section 8 only read, set session settings and use transaction control. Never run a big `generate_series` in a `FROM` clause there: PostgreSQL writes the whole series to disk first. In the select list it streams.
- **Never use ports 3000–3002** and don't start a second Vite dev server. The API is usually running from Visual Studio, which locks `bin/`: build with `-o` into a scratch folder.
- **Never commit.**
