# 0.7g Accounts module and the rules as a test

## 1. Goal

The last project with an old name, `MDBNavigator.Infrastructure.Accounts`, becomes the Accounts module, `src/Modules/Accounts/MDBNavigator.Accounts`. A small test project then states the dependency rules of the whole solution as a test, so a wrong project reference fails the build's tests instead of being noticed in review. The README and the working notes describe the structure as it now is.

Roadmap step **0.7g** ([ROADMAP.md](../ROADMAP.md), "0.7 Modular structure"), the last one of 0.7. No behavior change. The smoke tests of 0.7b must pass without any change to them.

Docs it changes: `README.md` ("Repository layout", a new "Architecture" section), `docs/ROADMAP.md` (plan link), two UI comments, the owner's local `CLAUDE.md` (paths, and the architecture rules).

## 2. Decisions

- **Accounts is one project, not Core plus Infrastructure.** It is almost entirely ASP.NET Core Identity wiring (sign-in, external providers, email, the account page's operations, the Data Protection keys); a core without ASP.NET Core would be nearly empty. This was agreed with the owner on 2026-11-14.
- **Namespace `MDBNavigator.Accounts`** (with `.Identity`, `.Email`, `.Persistence` as today). The migrations keep their ids and their folder; only their namespace and the type names they mention change.
- **The registration class is named like the other modules':** `AccountsServiceRegistration` becomes `AccountsModule`. Its two methods and `PasswordMinLength` keep their names.
- **Nothing references Accounts except the API**, and Accounts references only the SharedKernel. Other modules know a user only as the id in the session key.
- **The dependency rules become a test** in `tests/MDBNavigator.Architecture.Tests`: it reads the project files under `src/` and compares each project's references with a table. It needs no Docker and no build of the projects it checks, so it runs everywhere, CI included (0.4c).
- **The test finds the repository through its own source file path** (`[CallerFilePath]`), not through the output folder: tests are often built into a scratch folder here (`-o`), which is not inside the repository.

### The architecture test

`MDBNavigator.Architecture.Tests.csproj`: packages `coverlet.collector`, `Microsoft.NET.Test.Sdk`, `xunit`, `xunit.runner.visualstudio`; `<IsPackable>false</IsPackable>`; `<Using Include="Xunit" />`; no project references. First line inside `<Project>`:

```xml
  <!-- The solution's dependency rules as tests. Reads the project files under src/; needs no Docker and builds none of them. -->
```

`ProjectReferenceTests` (namespace `MDBNavigator.Architecture.Tests`):

```csharp
// Which project may reference which. A new project, or a new reference, has to be added here on purpose.
public class ProjectReferenceTests
{
    private static readonly Dictionary<string, string[]> Allowed = new()
    {
        ["MDBNavigator.SharedKernel"] = [],
        ["MDBNavigator.Providers.Abstractions"] = [],
        ["MDBNavigator.Providers.PostgreSQL"] = ["MDBNavigator.Providers.Abstractions"],
        ["MDBNavigator.Accounts"] = ["MDBNavigator.SharedKernel"],
        ["MDBNavigator.Connections.Contracts"] = ["MDBNavigator.Providers.Abstractions"],
        ["MDBNavigator.Connections.Core"] = ["MDBNavigator.Connections.Contracts", "MDBNavigator.SharedKernel"],
        ["MDBNavigator.Connections.Infrastructure"] = ["MDBNavigator.Connections.Core"],
        ["MDBNavigator.Workbench.Core"] = ["MDBNavigator.Connections.Contracts", "MDBNavigator.SharedKernel"],
        ["MDBNavigator.Workbench.Infrastructure"] = ["MDBNavigator.Workbench.Core"],
        ["MDBNavigator.API"] =
        [
            "MDBNavigator.Accounts",
            "MDBNavigator.Connections.Infrastructure",
            "MDBNavigator.Providers.PostgreSQL",
            "MDBNavigator.Workbench.Infrastructure",
        ],
    };
}
```

Facts:

| Fact | Checks |
|---|---|
| `Every_project_under_src_is_in_the_table` | The names of all `*.csproj` files under `src/` (without extension) are exactly the keys of `Allowed`. |
| `Each_project_references_only_what_the_rules_allow` | A `[Theory]` over the keys (`[MemberData]`): the project's `<ProjectReference Include="...">` file names, without extension, sorted, equal its `Allowed` entry, sorted. The failure message names the project and lists what is extra and what is missing. |
| `Core_and_contract_projects_are_free_of_web_and_database_packages` | For `MDBNavigator.SharedKernel`, `MDBNavigator.Providers.Abstractions`, and every project whose name ends in `.Core` or `.Contracts`: no `<FrameworkReference>`, and no `<PackageReference>` whose name starts with `Microsoft.AspNetCore` or `Microsoft.EntityFrameworkCore` or equals `EFCore.NamingConventions`, `Npgsql` or `Dapper`. |

The repository root: a private helper `RepositoryRoot([CallerFilePath] string path = "")` that walks up from the test's own source file until a folder contains `MDBNavigator.slnx`. Project files are read with `XDocument.Load`; `bin` and `obj` folders are skipped when searching.

````
### Architecture

The backend is a modular monolith: one deployable API, three modules, each about one problem.

```
MDBNavigator.API ──► Accounts                  sign-in, providers, email, the account page
                 ├─► Connections               connect, guard, cache, saved connections
                 ├─► Workbench ──► Connections.Contracts
                 │                             schema tree, scripts, running queries
                 └─► Providers.PostgreSQL ──► Providers.Abstractions
```

- **Inside a module** dependencies point inward: Infrastructure → Core → Contracts → SharedKernel. Core holds the rules and names no web or database technology; Infrastructure holds the cache, SQLite, SignalR and the background workers.
- **Between modules** only a `Contracts` project is visible. The workbench opens a database through `IDatabaseConnector` and knows nothing else about connections. Nothing references Accounts: the other modules know a user only as the id in the session key.
- **A database provider** references only `Providers.Abstractions`. A second provider (MS SQL Server) is a new project next to the PostgreSQL one and one registration line.
- **A use case** is a command or a query with one handler (`ICommandHandler`, `IQueryHandler`). A controller action gets its handler injected; logging and validation are decorators around every handler. There is no mediator library.
- **What every module needs** is in the SharedKernel: the handler interfaces, the common errors, the session key, and `IUserDataEraser`, through which each module removes its own data when an account is deleted.
- The API wires the modules together and owns what belongs to none of them: rate limits, CAPTCHA, security headers, error mapping.

`tests/MDBNavigator.Architecture.Tests` checks the project references against these rules.
````

## 6. Edge cases & don'ts

- **Don't touch the smoke tests.**
- **Don't change a migration's id, class name, `Up` or `Down`.** Only the namespace lines and the type-name strings.
- **Never run `dotnet ef database update`, and never point the tools or a test at `src/MDBNavigator.API/data/mdbnavigator.db`.**
- **User secrets are not affected:** the id is in the API project, which does not move.
- **Delete the project's `bin/` and `obj/` before `git mv`.** If `git mv` fails with "Permission denied", stop and report (Visual Studio may have the solution open).
- **The architecture test must fail when a rule is broken.** Check it once by hand: add a reference from `MDBNavigator.Workbench.Core` to `MDBNavigator.Connections.Core` in the project file, run the test, see it fail with a message that names both projects, and take the reference out again.
- **Don't make the test depend on the solution being built**, and don't give it project references: it reads files.
- **Don't rewrite other parts of the README.** Only the rows and the section named in section 5.
- **Don't change the older plans in `docs/plans/`.**
