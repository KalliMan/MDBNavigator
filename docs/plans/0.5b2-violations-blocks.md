# 0.5b2 Violations and blocks

## 1. Goal

In the public demo, actions the server refuses are counted per guest session. At 20 (a setting), the session ends at once, the visitor's email is blocked from the demo for 24 hours (a setting), and the owner gets an email.

Roadmap 0.5b2. Changes README "Configuration" (Demo table), `docs/api.md` "Endpoints", `docs/security.md` "Public demo", `docs/specs/authentication.md` "Demo guests", `docs/ROADMAP.md` 0.5b2 row.

## 2. Decisions

Agreed with the owner on 2026-11-20:

- Violations are permission errors, refused connections and limit hits. 20 end the session and block the visitor for 24 hours.
- **The email only, no IP addresses** (changed from "address and email" on 2026-11-20). An address block is undone with a VPN in a minute, and storing addresses would need a sentence in the terms. The demo's safety comes from the read-only database, the guard and the limits; the block stops casual misuse and tells the owner, who can change the invite code if someone keeps coming back.
- The owner gets an email for every block (name and email in the email; never in logs).
- No keyword scanning of SQL. No change to the terms text (they already say access can be ended at any time).

My calls inside this plan:

- **What counts** (each counts 1):
  - *Permission denied:* a run fails with SQLSTATE `42501` (insufficient privilege) or `25006` (write in a read-only transaction: what `demo_reader`'s `INSERT`/`CREATE` hit first); a guest calls `/api/auth/account/*` or `/api/auth/manage/*` (the UI never does).
  - *Connection refused:* every failed connect or reconnect (guard refusal, `pg_hba` reject, wrong password, unreachable host), and a run refused by the guard.
  - *Limit reached:* the run's time or row limit, `57014` from a statement (the role's `statement_timeout`; a user's Cancel never reaches that branch), `53400` (`temp_file_limit`), `53300` (role connection limit), "a query is already running" (`MaxRunningQueriesPerUser`), the failed-connect wait or its CAPTCHA, and the `Connect` and `Query` rate limits.
  - *Not counted:* syntax errors, missing tables and other mistakes (people trying a database make them), Cancel, results cut at `MaxRowsPerResultSet` (shown, not refused: `select * from demo.measurements` must stay harmless), expired connections.
- **The count is per session** (per throwaway account), in memory. A restart forgets counts, not blocks. 3 sessions a day × 19 is the most a visitor gets without a block; acceptable.
- **The block is in the database:** `demo_visitors.blocked_until_utc`.
- **A block ends every running session of that visitor** (two links can make two sessions).
- **What a blocked visitor sees:** a start with a link they already have gets 403 "Demo access is paused for 24 hours after too many refused actions." (the link stays unused). A link request for a blocked email gets the usual 204 and no email: the answer must not tell which emails are blocked.
- **The guest learns their session ended** three ways: the run that ended it says so in its Error tab; the countdown checks `/api/auth/me` every 30 seconds and goes to `/demo/ended` on a 401; any other request already gets 401. The start page names the rule beforehand, the ended page afterwards. No new SignalR message.
- **The counting interface lives in SharedKernel** (`IViolationRecorder`), implemented by Accounts only with `Demo:Enabled`. Connections and Workbench take it as an optional constructor parameter (like `IDatabaseErrorDescriber?` in `QueryExecution`), so without the demo nothing changes and no module references Accounts.
- **The provider classifies its errors:** `IDatabaseErrorDescriber.Classify(Exception)` returns a provider-neutral `DatabaseErrorKind`, so Workbench never names a SQLSTATE.

## 5. Contracts

### Settings (`Demo`)

| Key | Default | Validation (with `Enabled`) |
|---|---|---|
| `ViolationsBeforeBlock` | `20` | at least 1 (joins "the Demo limits must be at least 1") |
| `BlockHours` | `24` | 1–168: "Demo:BlockHours must be between 1 and 168" |

### SharedKernel

```csharp
namespace MDBNavigator.SharedKernel.Violations
{
    public enum ViolationKind { PermissionDenied, ConnectionRefused, LimitReached }

    // Something this server refused a signed-in user. Only the public demo counts them (Accounts, DemoViolations):
    // enough of them end a guest's session and block the visitor. Without the demo nothing implements this, so callers
    // take it as an optional constructor parameter.
    public interface IViolationRecorder
    {
        // userId: the account (SessionKey.UserIdOf). True when this violation ended the user's session.
        // Never throws; the block isn't cancelled by the caller going away.
        Task<bool> RecordAsync(string userId, ViolationKind kind);
    }
}
```

### Providers

```csharp
namespace MDBNavigator.Providers.Abstractions
{
    // Why a database refused a statement, in terms every provider can map to.
    public enum DatabaseErrorKind { Other, PermissionDenied, LimitReached }
}
// IDatabaseErrorDescriber gains:
DatabaseErrorKind Classify(Exception exception);
```

`PostgresErrorDescriber.Classify`: not a `PostgresException` → `Other`; `SqlState` `42501`, `25006` → `PermissionDenied`; `57014`, `53400`, `53300` → `LimitReached`; anything else → `Other`. Use `PostgresErrorCodes` constants (`InsufficientPrivilege`, `ReadOnlySqlTransaction`, `QueryCanceled`, `ConfigurationLimitExceeded`, `TooManyConnections`).

### Data (migration `AddDemoVisitorBlocks`)

- `demo_visitors.blocked_until_utc`: `DateTime?`, null. Left as it is when the block is over (the checks compare with now); the row goes after 90 days as before.

### `DemoAccess` changes

- `StartAsync`: right after the link is found valid and the visitor looked up, and before the limits: `visitor?.BlockedUntilUtc > now` → `DemoStartOutcome.Blocked` (new enum value; the link stays unused).
- `RequestJoinLinkAsync` and `RequestSignInLinkAsync`: when the address belongs to a visitor with `BlockedUntilUtc > now`, log "Demo link not sent: the visitor is blocked" and return (same answer).

### `DemoViolations` (singleton, `IViolationRecorder`)

- Constructor: `IServiceScopeFactory`, `DemoOptions`, `TimeProvider`, `ILogger<DemoViolations>`.
- State: one `SemaphoreSlim(1, 1)` around everything (violations are rare; at most a few guests); `Dictionary<string, Tally>` keyed by user id. `Tally`: `bool IsGuest`, `Guid VisitorId`, `int[] Counts` (by `ViolationKind`), `bool Ended`, `DateTime LastAtUtc`.
- `RecordAsync(userId, kind)`:
  1. Not a `Guid` (e.g. `SessionKey.LocalUserId`) → false.
  2. No tally yet: in a new scope, find the session row with `UserId == id && EndsAtUtc > now`. None → store a tally with `IsGuest = false`. Found → `IsGuest = true` with its visitor id.
  3. `!IsGuest` or `Ended` → false. Else count it, set `LastAtUtc`.
  4. Total below `ViolationsBeforeBlock` → false. Else set `Ended = true`, block (below), return true.
  - Any exception in 2: log the error, return false.
- Block, in a new scope, with `CancellationToken.None`:
  1. In one transaction: the visitor's `BlockedUntilUtc = max(existing, now + BlockHours)`; every session of that visitor with `EndsAtUtc > now` gets `EndsAtUtc = now`.
  2. If the account still exists, `GuestSessions.DeleteAccountAsync(user, CancellationToken.None)`. Other sessions of the visitor are deleted by the clean-up within a minute; their cookies stop at once (`GuestSessionValidator`).
  3. Log warning: "Demo guest blocked after {Violations} refused actions ({PermissionDenied} permission, {ConnectionRefused} connection, {LimitReached} limit)". No name, email or user id.
  4. `DemoEmails.SendInBackground(delivery, EmailTemplates.DemoVisitorBlocked(...), "demo block", logger)` with `IEmailDelivery` from the scope.
  - If the block throws: log the error, keep `Ended = true` (no retry storm), return true.
- `public void Forget(DateTime olderThanUtc)`: removes tallies with `LastAtUtc` before it.

### `DemoCleanup` addition

`scope.ServiceProvider.GetService<DemoViolations>()?.Forget(now.AddDays(-1))` at the end of a run.

### Where violations are recorded

| Place | When | Kind |
|---|---|---|
| `ConnectionOpener.ConnectAsync`, catch that records the limiter failure | any failed open | `ConnectionRefused` |
| `ConnectionOpener.RequireCaptchaOrWaitAsync` | before each of its three throws | `LimitReached` |
| `QueryExecution`, run-limit branch | time or row limit | `LimitReached` |
| `QueryExecution`, `DbException` branch | `Classify` gives `PermissionDenied` / `LimitReached` | same |
| `QueryExecution`, `ConnectionNotAllowedException` | always | `ConnectionRefused` |
| `RunQueryCommandHandler.Handle` | before throwing "already running" | `LimitReached` |
| `RateLimitPolicies` `OnRejected` | policy `Connect` or `Query` and the user has a `NameIdentifier` | `LimitReached` |
| `AuthEndpoints` guest filter on `account` and `manage` | the 403 | `PermissionDenied` |

- In `QueryExecution`, decide the kind inside the catch blocks, but call `RecordAsync` after the `try/finally` and before `SendCommandFinished`, so the registry is completed first. When it returns true: `error += "\n\nThis session has ended after too many refused actions."` (status stays `Failed`).
- `RunQueryCommandHandler.Handle` becomes `async`.
- `OnRejected` gets the policy name from the endpoint: `context.HttpContext.GetEndpoint()?.Metadata.GetMetadata<EnableRateLimitingAttribute>()?.PolicyName` (controllers use the attribute; `RequireRateLimiting` adds the same metadata). Only `Connect` and `Query` count.
- `IViolationRecorder` comes from `RequestServices.GetService` in the API places (null without the demo).

## 6. Edge cases & don'ts

- Never log names, emails or user ids. The owner's email carries them; the log carries counts.
- Don't store IP addresses (owner's decision).
- Don't count non-guests: the owner's own account on the demo server, and `Auth:Mode = None`'s `local` user.
- Don't count mistakes (syntax errors, missing tables) or cut results. Don't scan SQL.
- Don't tell a link request which emails are blocked (204, no email).
- Don't record inside `ConnectionOpener` when the client went away (the existing `when (!ct.IsCancellationRequested)` filter covers it).
- Don't call `RecordAsync` before `QueryExecution`'s registry entry is completed.
- Don't pass the request's `CancellationToken` into the block: a guest closing the tab must not stop it.
- Don't reference Accounts from Connections or Workbench; only `SharedKernel.Violations`. No new project or project reference.
- `RecordAsync` must not throw into the callers, so a counting bug never turns a normal error into a 500.
- Don't change existing API test classes.
- The demo's own connect (`/api/demo/connect`) goes through `ConnectionOpener` too: if the sample database is down, each retry counts. Fine (a guest won't retry 20 times in 10 minutes); the security doc says so.
