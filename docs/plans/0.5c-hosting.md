# 0.5c Hosting

## 1. Goal

The public demo runs on a small rented server at `https://mdbnavigator.com` and keeps running: Caddy in front for HTTPS, DNS and mail records at Cloudflare, sending through Brevo, automatic security updates, a weekly rebuild with fresh base images, and an outside uptime monitor.

Roadmap step **0.5c** ([ROADMAP.md](../ROADMAP.md), "0.5 Live demo"). It builds on 0.5a (`compose.demo.yaml`), 0.5b1–b3 (guests, start page) and 0.4a (`ReverseProxy:TrustedNetworks`, `/health`).

The step has two parts:

- **Part A, in the repository** (the implementer builds it): Caddy in `compose.demo.yaml`, the server's update script and timer, the CI check, and the docs, including a step-by-step guide `docs/hosting.md`. **No application code changes.**
- **Part B, on the server** (the owner does it, following `docs/hosting.md`, after Part A is committed and pushed): rent the server, DNS and mail records, first start, checks.

Docs it changes: `README.md` ("Public demo setup"), `docs/security.md` ("Public demo": a new "HTTPS and the server" part), `docs/ROADMAP.md` (0.5c row), `.env.example`, the owner's local `CLAUDE.md` (Demo Compose bullet, link to the guide). New: `docs/hosting.md`.

## 2. Decisions

Confirmed by the owner on 2026-11-20 (answers to four questions):

- **Address: `mdbnavigator.com`**, the root. The start page (0.5b3) is the landing page; `www.mdbnavigator.com` redirects to it.
- **Cloudflare's proxy is off (DNS only, grey cloud) for every record.** TLS ends on our server, not at Cloudflare (which would otherwise see guests' emails and cookies); Caddy gets certificates itself; the app sees each visitor's address through one proxy hop, exactly what 0.4a built (`ForwardLimit` 1). The server's IP address is public; the app's own rate limits and the demo caps carry the load.
- **Server: Hetzner Cloud, smallest shared x86 plan with 2 vCPU and 4 GB RAM** (about €4–5 a month with an IPv4 address), an EU location, Ubuntu 24.04 LTS, plus a **4 GB swap file**: the images are built on the server, and the UI build alone may use up to 4 GB (`NODE_OPTIONS=--max-old-space-size=4096`).
- **Uptime monitor: UptimeRobot (free)** on `https://mdbnavigator.com/health`, every 5 minutes, emailing the owner.

My calls inside this plan (listed for the owner in the summary; change any before building):

- **Caddy lives in `compose.demo.yaml`**, as 0.5a planned, so the demo is still one command. Image `caddy:2.11-alpine` (2.11.9 on 2026-11-20): the minor version is pinned, its patch releases come with the weekly pull.
- **One setting for the address: `MDBNAV_DOMAIN`** (e.g. `mdbnavigator.com`). It replaces `MDBNAV_APP_URL`: `Email:AppBaseUrl` becomes `https://${MDBNAV_DOMAIN}`, so Caddy's certificate and the emailed links can't disagree. Nothing is deployed yet, so nobody's `.env` breaks.
- **The app trusts forwarded headers only from Caddy's network.** A new network `proxy-net` with a fixed range (`MDBNAV_PROXY_SUBNET`, default `172.30.254.0/24`) holds only Caddy and the app; `ReverseProxy__TrustedNetworks__0` is the same value. Trusting all of Docker's ranges would work too, but would also trust the sample database's container and the host. The variable exists so a test run next to another one can pick another range.
- **Caddy replaces any `X-Forwarded-For` a visitor sends** (its default when no `trusted_proxies` is set; checked on 2026-11-20 with a throwaway container: a sent `1.2.3.4` became the real address). No `trusted_proxies`.
- **Caddy removes `Server` and `Via`** (both name Caddy; Kestrel's `Server` is already removed for the same reason). It adds no security headers: the app sets them.
- **Compression only for `/assets/*`** (the built UI's hashed files; Monaco is several MB). API answers stay uncompressed: compressing a secret next to text a visitor controls can leak it (BREACH).
- **No access log in Caddy:** URLs carry invite codes and sign-in links, and addresses are personal data.
- **IPv4 only: no `AAAA` record.** Docker hands IPv6 connections to a container from its own address unless IPv6 is set up on its networks, so every IPv6 visitor would share one address and its limits (3 guest sessions per address per hour). IPv6-only clients still reach IPv4 sites through their provider.
- **HTTP/3 on**: UDP 443 is published and allowed; browsers fall back to HTTP/2 if it fails.
- **Ports configurable for test runs only:** `MDBNAV_HTTP_PORT` (80), `MDBNAV_HTTPS_PORT` (443). The app's `127.0.0.1:8080` from `docker-compose.yml` stays: reachable only on the server itself, handy for checks over SSH.
- **Firewall at the provider (Hetzner Cloud Firewall), not ufw:** Docker's published ports bypass ufw, and a firewall outside the server can't be undone from inside it. Inbound: TCP 22, 80, 443, UDP 443, ICMP.
- **SSH: keys only, no root login,** one sudo user `mdbnav` (also in the `docker` group). No fail2ban: with passwords off, it would only thin the log.
- **Automatic updates:** Ubuntu's unattended-upgrades for security updates and also **Docker's packages** (the engine keeps the containers apart), with an **automatic reboot at 04:30 UTC** when an update needs one. `restart: unless-stopped` brings the containers back.
- **Weekly rebuild, Sunday 03:30 UTC** (`deploy/update.sh` from a systemd timer): pulls Caddy, rebuilds the app and the sample database on fresh base images (.NET, Node, PostgreSQL 17), restarts what changed, prunes old images and build cache. **It never runs `git pull`:** new code goes live only when the owner pulls it and runs the same script. A guest in a session at that moment loses it; acceptable at that hour.
- **The repository on the server:** `/opt/mdbnavigator`, a clone of the public GitHub repository over HTTPS (no credentials on the server). The server's `.env` sets `COMPOSE_FILE=docker-compose.yml:compose.demo.yaml`, so a plain `docker compose ...` there can't start the setup without the demo's locks by mistake.
- **No backups** (Hetzner's backup option off). The SQLite volume holds the visitor list, which the terms promise to delete 90 days after the last visit; a backup would keep it longer. Everything else is rebuilt from the repository and `.env`, which the owner keeps in a password manager. Losing the volume costs the visitor list, the admin account (seeded again) and sign-ins (Data Protection keys).
- **The Data Protection warning stays** ("No XML encryptor configured", at every start): the keys that sign cookies sit unencrypted in the SQLite file. Whoever can read the volume already controls the server. Documented in `docs/security.md`, not silenced.
- **Mail:** the sender is `support@mdbnavigator.com` (`MDBNAV_EMAIL_FROM`), the address already routed to the owner by Cloudflare Email Routing, so a reply to a sign-in email reaches the owner. Brevo's domain authentication records exactly as Brevo shows them, DNS only. One SPF record (Cloudflare's, with Brevo's include added only if Brevo asks for one). **DMARC** starts at `p=none` and becomes `p=quarantine` once a test email shows DKIM and DMARC passing.
- **DNSSEC on** at Cloudflare (one switch). **No CAA record:** Caddy may fall back to a second certificate authority, and a CAA record would have to name both.
- **`SavedConnections:PasswordKey` stays unset** on the demo, as `docs/security.md` advises for instances strangers use.
- **The admin account exists on the public site** (`Auth:Admin`): its password is long and random (`openssl rand -base64 24`).

## 5. Contracts

### 5.1 `docker/caddy/Caddyfile`

Exactly (tabs for indentation):

```
# The public demo's front door (compose.demo.yaml). Caddy gets and renews the certificates itself (Let's Encrypt),
# redirects HTTP to HTTPS, and passes requests on to the app. MDBNAV_DOMAIN comes from .env, e.g. mdbnavigator.com.
# Why each choice: docs/security.md, "Public demo".

{$MDBNAV_DOMAIN} {
	# The app sets the security headers itself. Caddy's own Server and Via headers go, as Kestrel's Server header
	# does: they only tell an attacker what to look up.
	header {
		-Server
		-Via
	}

	# Only the built UI's files (Monaco is several MB). Compressing answers that hold a secret next to text a visitor
	# controls can leak the secret (BREACH), so API answers stay as they are.
	@assets path /assets/*
	encode @assets zstd gzip

	# Caddy replaces any X-Forwarded-For a visitor sends with the address it sees, and sets X-Forwarded-Proto; the app
	# trusts both only from proxy-net (ReverseProxy:TrustedNetworks). No trusted_proxies: nothing is in front of Caddy
	# (Cloudflare's proxy is off), and with it a visitor could fake their address.
	# No access log: URLs carry invite codes and sign-in links, and addresses are personal data.
	reverse_proxy app:8080
}

www.{$MDBNAV_DOMAIN} {
	header {
		-Server
		-Via
	}
	redir https://{$MDBNAV_DOMAIN}{uri} permanent
}
```

    # pulls its patch releases every week.
    image: caddy:2.11-alpine
    environment:

      - "${MDBNAV_HTTPS_PORT:-443}:443"
      # HTTP/3.
      - "${MDBNAV_HTTPS_PORT:-443}:443/udp"

      - proxy-net

      - app

    deploy:
      resources:
        limits:
          cpus: "0.5"
          memory: 256M
    logging: *logging

### 5.4 `deploy/update.sh`

```sh
#!/bin/sh
# Rebuilds the public demo on its server with fresh base images and restarts what changed (docs/hosting.md).
#   sh deploy/update.sh
# The weekly timer (mdbnavigator-update.timer) runs it too. It never pulls code: new code goes live only when the
# owner runs git pull first.
set -eu
cd "$(dirname "$0")/.."

compose() {
    docker compose -f docker-compose.yml -f compose.demo.yaml "$@"
}

# Caddy is a ready-made image. The app and the sample database are built here on fresh base images (.NET, Node,
# PostgreSQL 17), so their security fixes arrive without a code change.
compose pull --ignore-buildable
compose build --pull
# Recreates only the containers whose image or settings changed. Data stays in the volumes.
compose up -d --remove-orphans
# Old images and build cache would fill the disk over the weeks.
docker image prune -f
docker builder prune -f
```

### 5.9 `docs/hosting.md`

Title `# Hosting the public demo`. Intro: how the demo at `mdbnavigator.com` is run: one small server, Docker Compose with `compose.demo.yaml` (the app, the sample database, Caddy), DNS at Cloudflare, email through Brevo. Anyone can run their own the same way with their own domain; replace `<domain>` everywhere. What the setup protects and why: [security.md, Public demo](security.md#public-demo). Never put real addresses, emails or secrets into this file.

Sections, in this order, with this content (prose in the docs' usual style; commands exactly as given):

**1. What you need.** Accounts: Hetzner Cloud, Cloudflare (the domain's DNS), Brevo (sending, with the domain authenticated), UptimeRobot. A password manager for the server's `.env`, the `mdbnav` user's password and the admin password. An SSH key (on Windows, in PowerShell: `ssh-keygen -t ed25519 -C "mdbnavigator-server"`; the public half is `~\.ssh\id_ed25519.pub`).

**2. The server.**
- First a **firewall** (Hetzner Console → Firewalls), named `mdbnavigator`, inbound: TCP 22, TCP 80, TCP 443, UDP 443, ICMP; outbound left open. Why the provider's firewall and not ufw (Docker's published ports bypass ufw; a firewall outside can't be switched off from inside).
- Then the **server**: an EU location; image Ubuntu 24.04; type shared vCPU, x86, the smallest with 2 vCPU and 4 GB RAM; public IPv4 and IPv6 both on (IPv6 costs nothing; it just gets no DNS record); the SSH key; the firewall above; backups **off** (why: the 90-day promise); name `mdbnavigator`. Note the IPv4 address.

**3. DNS at Cloudflare** (do it now: the records need a few minutes before the first start). Cloudflare → the domain → DNS → Records. **Every record "DNS only" (grey cloud)**; Cloudflare suggests "Proxied" for new records, switch it off. Table:

| Type | Name | Content | Proxy |
|---|---|---|---|
| A | `@` | the server's IPv4 address | DNS only |
| CNAME | `www` | `<domain>` | DNS only |

No `AAAA` record (why, one sentence: IPv6 visitors would share one address and its limits). DNS → Settings → **DNSSEC: Enable**. Check from your machine: `nslookup <domain> 1.1.1.1` and `nslookup www.<domain> 1.1.1.1` give the server's address.

**4. Mail records.**
- Cloudflare **Email Routing** (Email → Email Routing) already forwards `support@<domain>` to your own inbox, and added its MX, SPF (`TXT @ "v=spf1 include:_spf.mx.cloudflare.net ~all"`) and DKIM records. Leave them.
- **Brevo:** Senders, Domains & Dedicated IPs → Domains → add `<domain>` → Authenticate. Add exactly the records Brevo shows (a `brevo-code` TXT, DKIM records, a DMARC record), with these rules: every one DNS only (a proxied DKIM CNAME breaks DKIM); never a second SPF record: if Brevo asks for an SPF include, add it to the existing record (`v=spf1 include:_spf.mx.cloudflare.net include:<Brevo's> ~all`); the DMARC record is `_dmarc` TXT `v=DMARC1; p=none` for now. Press Verify in Brevo until it shows the domain authenticated. If Brevo asks for a verified sender, add `support@<domain>`.
- An **SMTP key**: Brevo → SMTP & API → SMTP → Generate a new SMTP key. The login shown there is `MDBNAV_SMTP_USERNAME`, the key `MDBNAV_SMTP_PASSWORD`.
- DMARC is tightened in section 8, after a test email.

**5. First login and the basics.** As root, once:

```sh
ssh root@<server address>
apt update && apt full-upgrade -y
adduser mdbnav                       # asks for a password: it's for sudo; keep it in the password manager
usermod -aG sudo mdbnav
install -d -m 700 -o mdbnav -g mdbnav /home/mdbnav/.ssh
install -m 600 -o mdbnav -g mdbnav /root/.ssh/authorized_keys /home/mdbnav/.ssh/authorized_keys
reboot
```

Then, in a **new** terminal, `ssh mdbnav@<server address>` must work before going on. Lock SSH down (keys only, no root):

```sh
sudo tee /etc/ssh/sshd_config.d/10-mdbnavigator.conf >/dev/null <<'EOF'
PermitRootLogin no
PasswordAuthentication no
KbdInteractiveAuthentication no
EOF
sudo sshd -t && sudo systemctl restart ssh
sudo sshd -T | grep -Ei '^(permitrootlogin|passwordauthentication|kbdinteractiveauthentication) '
```

The last command prints all three as `no`. Keep the first terminal open until `ssh mdbnav@...` still works from another one. (The `10-` prefix matters: the first value sshd reads wins, and Ubuntu's cloud image may ship a `50-cloud-init.conf` that allows passwords.)

Swap, for the builds:

```sh
sudo fallocate -l 4G /swapfile && sudo chmod 600 /swapfile && sudo mkswap /swapfile && sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
free -h        # Swap: 4.0Gi
timedatectl    # Time zone: Etc/UTC
```

**6. Docker and automatic updates.**
- Install Docker Engine from Docker's apt repository, as https://docs.docker.com/engine/install/ubuntu/ describes ("Install using the apt repository"; packages `docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin`). Then `sudo usermod -aG docker mdbnav`, sign out and in again, and `docker run --rm hello-world` works without sudo. Note: the `docker` group is as powerful as root; `mdbnav` is the only user.
- Automatic updates (Ubuntu's own security updates are on by default; this adds Docker's packages and the reboot):

```sh
cat /etc/apt/apt.conf.d/20auto-upgrades     # both lines end in "1"; if the file is missing: sudo dpkg-reconfigure -plow unattended-upgrades
apt-cache policy docker-ce | grep -m1 'o=Docker'   # shows o=Docker,...,l=Docker CE
sudo tee /etc/apt/apt.conf.d/52mdbnavigator >/dev/null <<'EOF'
// Docker's packages too: the engine is what keeps the containers apart.
Unattended-Upgrade::Origins-Pattern {
        "origin=Docker,label=Docker CE";
};
// Reboot for a new kernel at 04:30 UTC; the containers start again by themselves.
Unattended-Upgrade::Automatic-Reboot "true";
Unattended-Upgrade::Automatic-Reboot-Time "04:30";
EOF
sudo unattended-upgrade --dry-run --debug 2>&1 | grep -i 'allowed origins'   # lists origin=Docker,label=Docker CE
```

If `apt-cache policy` shows other `o=` or `l=` values than `Docker` and `Docker CE`, use those in the file.

**8. Checks.** From your own machine:

| Command | Shows |
|---|---|
| `curl -sI https://<domain>/` | `HTTP/2 200`, `strict-transport-security: max-age=31536000`, `content-security-policy`, no `server` or `via` line |
| `curl -sI http://<domain>/` | `308`, `location: https://<domain>/` |
| `curl -sI https://www.<domain>/x` | `301`, `location: https://<domain>/x` |
| `curl -s https://<domain>/health` | `Healthy` |
| `curl -m 5 http://<server address>:8080/` | times out (the app's own port is not reachable from outside) |
| `ssh root@<server address>` | `Permission denied (publickey)` |

The `strict-transport-security` line also proves the app trusts Caddy: the app sends it only when it believes the request came over HTTPS.

**12. When something is wrong.**
- No certificate: `docker compose logs caddy`. Usually DNS (section 3: the A and CNAME point at this server, DNS only) or the firewall (80 and 443). Don't restart again and again: Let's Encrypt allows 5 failed validations per hostname per hour.
- Every visitor seems to share one address, or `strict-transport-security` is missing: the app's log line "Forwarded headers are trusted from loopback and 1 configured networks: 172.30.254.0/24" must appear (`docker compose logs app | grep Forwarded`); `ReverseProxy__TrustedNetworks__0` and `proxy-net` must use the same `MDBNAV_PROXY_SUBNET`.
- Emails don't arrive: `docker compose logs app | grep -i smtp`, Brevo → Transactional → Logs.
- The build is killed (out of memory): `free -h` shows the swap.

```markdown
**HTTPS and the server**

- **Caddy** (`docker/caddy/Caddyfile`) gets the certificate from Let's Encrypt and renews it, redirects HTTP to HTTPS and `www.` to the domain, and passes requests on to the app. It adds no security headers (the app sets them) and removes its own `Server` and `Via` headers.
- **Cloudflare only answers DNS:** its proxy is off, so TLS ends on the demo's server and Cloudflare never sees guests' emails or cookies. Turning the proxy on would need Caddy's `trusted_proxies` with Cloudflare's ranges, or every visitor would get a Cloudflare address.
- **Visitors' addresses:** Caddy replaces any `X-Forwarded-For` a visitor sends with the address it sees. The app believes forwarded headers only from `proxy-net`, the network that holds just Caddy and the app (`MDBNAV_PROXY_SUBNET`, which is also `ReverseProxy:TrustedNetworks`).
- **IPv4 only:** the domain has no `AAAA` record. Docker passes IPv6 connections to a container from an address of its own, so every IPv6 visitor would share one address and its limits.
- **No access log:** URLs carry invite codes and sign-in links, and addresses are personal data.
- **Compression only for the UI's files** (`/assets/*`): compressing an answer that holds a secret next to text a visitor controls can leak the secret (BREACH).
- **Reachable from outside:** ports 80 and 443, and SSH with keys only (no passwords, no root). The provider's firewall allows nothing else; it sits outside the server because Docker's published ports bypass a firewall on the server itself. The app's port 8080 is published on `127.0.0.1` only, the database not at all.
- **Updates:** the system's security updates and Docker's packages install by themselves every day, with a reboot at 04:30 UTC when one needs it. Every Sunday at 03:30 UTC, `deploy/update.sh` rebuilds the images on fresh base images (.NET, PostgreSQL 17, Caddy 2.11) and restarts what changed. It doesn't pull new code. NuGet and npm packages are updated in the repository.
- **No backups:** the visitor list must be gone 90 days after the last visit, as the demo terms promise, and a backup would keep it longer. Everything else is rebuilt from the repository and the server's `.env`.
- **Data Protection keys** (they sign the sign-in cookies) are stored unencrypted in the SQLite file, which the log warns about at every start. Whoever can read that volume already controls the server, so they are not encrypted further.
```

## 6. Edge cases & don'ts

- **No application code changes.** If something seems to need one, stop and ask.
- **Don't add `trusted_proxies`** to the Caddyfile, and don't widen `ReverseProxy:TrustedNetworks` to all of Docker's ranges: either lets someone other than Caddy set a visitor's address.
- **The subnet appears twice** (`ReverseProxy__TrustedNetworks__0` and `proxy-net`): same variable, same default, or HSTS and per-address limits silently break.
- **Don't add security headers in Caddy**; only remove `Server` and `Via`. Two sets of headers drift apart (docs/security.md says so already).
- **Don't add a `log` directive** to the Caddyfile.
- **Don't compress everything** (`encode` without the `@assets` matcher).
- **Don't remove the app's `127.0.0.1` port** from `docker-compose.yml`, and never publish 8080 on all addresses.
- **Don't set `ASPNETCORE_HTTPS_PORT`** in the demo: Caddy does the redirect, and the app sees HTTPS through `X-Forwarded-Proto`.
- **Don't keep `MDBNAV_APP_URL` as an alias**: one setting for the address, everywhere (compose file, `.env.example`, CI, README).
- **`deploy/update.sh` must not `git pull`**, and must use the explicit `-f` files (it must work even if `COMPOSE_FILE` is missing from `.env`).
- **Real values never go into the repository:** no IP address, email, invite code or key in `docs/hosting.md`, `.env.example` or CI.
- **Test runs never touch the owner's setup:** another project name (`-p`), `--env-file` from the scratch folder (so the repository's `.env`, if any, isn't read), other ports and subnet, and a third `-f` file with other `image:` names. Never run `deploy/update.sh` on the owner's machine: it would rebuild and restart the owner's own `mdbnavigator` project.
- **`docker/caddy/Caddyfile` with LF endings**: `.gitattributes` already covers `docker/**`.
- **The scratch Caddyfile for tests imports the real one**, so the site blocks under test are the real ones; only `local_certs` is added.

- **A new setting, `MDBNAV_REDIRECT_DOMAINS`**: the names that redirect to the demo, separated by spaces. The Caddyfile's `www.{$MDBNAV_DOMAIN}` block became `{$MDBNAV_REDIRECT_DOMAINS}`. `compose.demo.yaml` defaults it to `www.${MDBNAV_DOMAIN}`, so a one-name setup works as planned: Caddy refuses a site block without a name, so the setting can't be empty. The demo's server sets `mdbnavigator.com www.mdbnavigator.com`.
- **The redirect is temporary (302), not permanent (301):** browsers remember a permanent redirect, and the root may serve something else one day.
- **DNS:** a third record, `A demo` → the server, DNS only. `docs/hosting.md` sections 3, 7, 8, 10 and 12, README, `docs/security.md`, ROADMAP and `.env.example` changed with it.
