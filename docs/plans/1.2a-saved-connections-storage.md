# 1.2a Saved connections: storage and API

## 1. Goal

Each user can keep a list of saved connections (name, server type, server, port, default database, user name, color) in the app's own SQLite database. The list is managed through a CRUD API under `/api/savedConnections`. With `Auth:Mode = None` the list belongs to the one local user. Backend only: the UI comes in 1.2b.

## 2. Decisions

All agreed with the owner on 2026-11-13. Each decision says which step builds it; only the ones marked **1.2a** are built here. The rest are written down here so the later plans don't have to settle them again.

### Split of 1.2 (all steps)

- **1.2a** Storage and API (this plan).
- **1.2b** Connect dialog: the saved list, save, edit, delete, connect from a saved entry (password typed each time), a color picker.
- **1.2c** Remember password: optional, encrypted, only offered when the key is configured.
- **1.2d** Switching a tab's server or database from the query bar.

### Built in 1.2a

- **Stored in the existing app database, through `AccountsDbContext`.** One SQLite file, one migrations history, and the startup migration already in place. The context and the `MDBNavigator.Infrastructure.Accounts` project are **not renamed**. A rename would touch every migration's designer file and the project references, and gain nothing but a name. Instead, the comments and the README row say that this project holds the app's own database.
- **The app database is now used with `Auth:Mode = None` too.** There, saved connections belong to the local user (`SessionKey.LocalUserId` = `"local"`). Identity is still not registered in None mode. The database is created and migrated in both modes, and roles and the admin are seeded only with `Accounts`. This changes the spec: until now, None mode "needs no app database".
- **The owner is a plain text column `owner_id`, with no foreign key to `users`.** It holds the same string the session key uses: the account's GUID as `Guid.ToString()`, or `"local"`. Why not a foreign key: the local user has no row in `users`, and SQLite treats NULLs as distinct in a unique index, so "null means local" would quietly lose the unique-name rule. The price is that deleting an account must delete its saved connections itself. `AccountManagement.DeleteAsync` does that in the same transaction as deleting the user.
- **Switching modes doesn't move connections.** Rows saved under `"local"` are not visible to accounts, and the other way round. They stay in the database untouched. The README says so in one sentence.
- **Names are unique per owner, ignoring case.** This follows Identity's own pattern: a `normalized_name` column (`Name.Trim().ToUpperInvariant()`) with a unique index on `(owner_id, normalized_name)`. It works the same on any database server, unlike SQLite's `NOCASE`, which only folds ASCII. The handlers check first so they can give a clear 409; the index is the backstop.
- **At most 100 saved connections per user** (`SavedConnectionLimits.MaxPerUser`, a constant rather than a setting). On a public instance this caps what one account can store. The 101st gives 409.
- **Color is the user's choice, or null.** It is stored as `#rrggbb` in lower case. Null means "use the hashed color", meaning the UI's `pickConnectionColor` stays the fallback. The server accepts any `#rrggbb`. In 1.2b the UI offers the six colors of `CONNECTION_COLORS`.
- **Default database is optional** (`databaseName`, null when empty). 1.2a only stores it. 1.2b decides how it is used, for example as the database new query tabs open in.
- **No password in 1.2a.** The request DTO has no password property, and System.Text.Json ignores unknown JSON properties, so a password the UI sends is dropped and never stored. 1.2c adds the column and its own migration.
- **Another user's id gives 404, never 403**, so ids don't reveal that a row exists. Ids are version 7 GUIDs, like `ApplicationUser`.
- **No rate-limit policy on these endpoints.** They are small SQLite writes, already behind sign-in, and the 100-row cap bounds storage. The existing `Connect` and `Query` policies are about opening connections to other hosts, which this doesn't do.
- **The connection guard is not checked on save.** Saving a blocked host is harmless; connecting to it is still refused by `ConnectionGuard`, as today.
- **Timestamps** (`created_at_utc`, `updated_at_utc`) are stored but not returned. EF Core reads SQLite `DateTime` values back as `DateTimeKind.Unspecified`, so returning them would need a UTC converter, and no UI needs them yet.

### For later steps (recorded now, not built here)

- **1.2b, dialogs:** stay with our own components (`ModalWindow`, `Select`, `Input`); no Radix or shadcn. The connect dialog doesn't need them.
- **1.2b, color picker:** the six `CONNECTION_COLORS` plus "automatic" (null).
- **1.2c, password encryption:** AES-GCM (`System.Security.Cryptography.AesGcm`) with a 32-byte key read from the setting `SavedConnections:PasswordKey`, given as base64 through an environment variable (`SavedConnections__PasswordKey`) or user secrets, never `appsettings*.json`. Not ASP.NET Core Data Protection: its keys live in the same SQLite file as the passwords would, so anyone with the file could decrypt them. Without the key the option isn't offered, and stored passwords are ignored.
- **Read-only connections:** not in 1.2. They move to Phase 3 ("Roles and permissions per connection"). When they come: `SET default_transaction_read_only` (PostgreSQL) for the connection.

### `Features/SavedConnections/SavedConnectionInputValidator.cs`

Rules, all on the **trimmed** value (the handlers store trimmed values, so lengths are checked on what gets stored):

| Field | Rule | Message |
|---|---|---|
| `Name` | not null or whitespace | `Name is required.` |
| `Name` | trimmed length ≤ `NameMaxLength` | `Name must be at most 100 characters.` |
| `ServerType` | `!= ServerType.None` | `ServerType is missing or not supported.` (same as connect) |
| `ServerName` | not null or whitespace | `ServerName is required.` |
| `ServerName` | trimmed length ≤ `ServerNameMaxLength` | `ServerName must be at most 253 characters.` |
| `Port` | `InclusiveBetween(1, 65535)` | `Port must be between 1 and 65535.` |
| `DatabaseName` | null/whitespace, or trimmed length ≤ `DatabaseNameMaxLength` | `DatabaseName must be at most 128 characters.` |
| `UserName` | not null or whitespace | `UserName is required.` |
| `UserName` | trimmed length ≤ `UserNameMaxLength` | `UserName must be at most 128 characters.` |
| `Color` | null/empty, or matches `^#[0-9a-fA-F]{6}$` | `Color must be a hex color like #16a34a.` |

Build the messages from the constants (`$"Name must be at most {SavedConnectionLimits.NameMaxLength} characters."`). Use `.Must(...)` for the trimmed checks, for example `RuleFor(x => x.Name).Must(n => !string.IsNullOrWhiteSpace(n))`, then `.Must(n => n.Trim().Length <= …)` with `.When(x => !string.IsNullOrWhiteSpace(x.Name))`. Use `Regex` with `RegexOptions.CultureInvariant`, or FluentValidation's `.Matches(...)` under a `.When(...)` for non-empty colors.

### `Features/SavedConnections/SavedConnectionMapping.cs`

```csharp
using MDBNavigator.Application.DTOs;
using MDBNavigator.Domain.Entities;
using MDBNavigator.Domain.Enums;

namespace MDBNavigator.Application.Features.SavedConnections
{
    // One place that turns input into stored values (trimmed, empty optional values as null, color in lower case)
    // and stored values into the DTO.
    public static class SavedConnectionMapping
    {
        public static string NormalizeName(string name) => name.Trim().ToUpperInvariant();

        // Sets everything the user controls and UpdatedAtUtc. Id, OwnerId and CreatedAtUtc are left alone.
        public static void Apply(SavedConnectionInput input, SavedConnection target, DateTime nowUtc)
        {
            target.Name = input.Name.Trim();
            target.NormalizedName = NormalizeName(input.Name);
            target.ServerType = input.ServerType;
            target.ServerName = input.ServerName.Trim();
            target.Port = input.Port;
            target.DatabaseName = string.IsNullOrWhiteSpace(input.DatabaseName) ? null : input.DatabaseName.Trim();
            target.UserName = input.UserName.Trim();
            target.Color = string.IsNullOrWhiteSpace(input.Color) ? null : input.Color.Trim().ToLowerInvariant();
            target.UpdatedAtUtc = nowUtc;
        }

        public static SavedConnectionDto ToDto(SavedConnection c) => new(c.Id, c.Name, ServerTypes.NameOf(c.ServerType),
            c.ServerName, c.Port, c.DatabaseName, c.UserName, c.Color);
    }
}
```

**Create handler**, in this order:
1. `CountAsync(UserId) >= MaxPerUser` → `throw new ConflictException($"You can save up to {SavedConnectionLimits.MaxPerUser} connections. Delete one first.")`
2. `NameExistsAsync(UserId, NormalizeName(Input.Name), null)` → `throw new ConflictException($"A saved connection named \"{Input.Name.Trim()}\" already exists.")`
3. `var now = DateTime.UtcNow; var entity = new SavedConnection { OwnerId = UserId, CreatedAtUtc = now }; SavedConnectionMapping.Apply(Input, entity, now);`
4. `await _store.AddAsync(entity)`, then return `ToDto(entity)`.

**Update handler:**
1. `FindAsync(UserId, Id)`, null → `ObjectNotFoundException("Saved connection not found.")`
2. `NameExistsAsync(UserId, NormalizeName(Input.Name), Id)` → same `ConflictException` as create
3. `Apply(Input, entity, DateTime.UtcNow)`, `SaveChangesAsync`, return `ToDto(entity)`.

### `AccountManagement.DeleteAsync`

Add `AccountsDbContext db` to the constructor (`private readonly AccountsDbContext _db;`). Replace the `_userManager.DeleteAsync(user)` part with:

```csharp
// Saved connections have no foreign key to users (see AccountsDbContext), so they are removed here, in the same
// transaction: the account and its connections go together, or neither does. UserManager uses this same scoped
// context, so its delete runs inside the transaction.
var ownerId = user.Id.ToString();
await using var transaction = await _db.Database.BeginTransactionAsync();
await _db.SavedConnections.Where(c => c.OwnerId == ownerId).ExecuteDeleteAsync();

var result = await _userManager.DeleteAsync(user);
if (!result.Succeeded)
{
    // Disposing the transaction without committing rolls the connections' delete back.
    return result;
}

await transaction.CommitAsync();
```

## 6. Edge cases & don'ts

- **Never take the owner from the request body or a header other than the session.** It is always `UserId` from `BaseApiController`, derived from the sign-in.
- **Every store query filters by owner**, including `FindAsync` and `DeleteAsync`. Don't add a "find by id" without the owner.
- **No password anywhere in 1.2a**: not in the entity, the DTOs, the migration or the logs. Don't add a `Password` property "for later"; 1.2c adds it with its own migration and encryption.
- **No personal data in logs.** `LoggingBehavior` logs only request type names; don't log server names, user names or connection names.
- **Don't add a foreign key from `saved_connections` to `users`**, and don't make `owner_id` nullable (see Decisions).
- **Don't use SQLite `NOCASE` or any SQLite-only SQL** in the mapping; uniqueness goes through `normalized_name` (spec: "no SQLite-specific SQL outside startup").
- **Don't rename `AccountsDbContext` or the project**, and don't edit the existing `InitialCreate` migration.
- **Don't return timestamps** in the DTO (see Decisions: `DateTimeKind`).
- **Validation runs before the handler** (`ValidationBehavior`), on the raw input. That's why the validator checks trimmed values, and `Apply` trims again when storing.
- **Duplicate-name race:** two simultaneous creates with the same name could both pass the check. The unique index then fails the second with a `DbUpdateException`, which becomes a 500. This is accepted (one person editing their own list); don't add SQLite error-code parsing for it.
- **Missing required JSON properties** (`required` in `SavedConnectionRequest`) give ASP.NET Core's own `400` problem response, as `ConnectionSettingsQuery` does today. Leave it.
- **None mode now opens SQLite at startup.** If `ConnectionStrings:AppDb` points to a folder that can't be created, None mode now fails at startup where it didn't before. That is intended and covered by the README row; don't catch it.
- **Don't touch the UI.** `serverTypeOptions.ts`, the connect dialog and `connectionColor.ts` stay as they are until 1.2b.
- **Don't commit.** Finish with the summary, what was verified, and a commit message.
