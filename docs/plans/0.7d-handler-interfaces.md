# 0.7d Own handler interfaces

## 1. Goal

Replace MediatR with our own handler interfaces, in a new `MDBNavigator.SharedKernel` project: commands and queries, their handlers, and decorators for logging and validation. Controllers get the handler they need injected into the action, so there is no dispatcher. MediatR was held on 12.4.1 because later versions are commercial; after this step it is gone.

Roadmap step **0.7d** ([ROADMAP.md](../ROADMAP.md), "0.7 Modular structure"; it was 0.6c). No behavior change for the API: the same endpoints, status codes, JSON and hub messages. The smoke tests of 0.7b must pass without any change to them.

Docs it changes: `README.md` ("Repository layout", "Tech stack"), `docs/ROADMAP.md` (plan link), the owner's local `CLAUDE.md` (conventions).

## 2. Decisions

- **Mirrors What2Eat's SharedKernel**, without its Result type: `ICommand`, `ICommand<TResponse>`, `IQuery<TResponse>`, `ICommandHandler<TCommand>`, `ICommandHandler<TCommand, TResponse>`, `IQueryHandler<TQuery, TResponse>`, a logging and a validation decorator, `AddHandlersFromAssembly` and `AddHandlerDecorators`.
- **Handlers return their value and throw the existing exceptions**, as today. The Result pattern would change the error contract with the UI and is not part of 0.7.
- **No dispatcher.** A controller action takes the one handler it calls as a `[FromServices]` parameter. Constructors with a dozen handlers would be worse, and one injected "sender" is a dispatcher again.
- **Commands without a value implement `ICommand`**, not `ICommand<Unit>`; their handler returns `Task`.
- **The validation decorator throws `FluentValidation.ValidationException`**, exactly as the MediatR behavior does today, so the middleware and the 400 answers stay the same.
- **Logging changes on purpose:** one line per request after it succeeded, with its duration (`{RequestName} handled in {ElapsedMs} ms`), instead of a line before and a line after. A failure is logged by the exception middleware, as today. The request itself is never logged: it can hold a database password.
- **Handlers are registered scoped** (MediatR registered them transient). They keep no state, so nothing changes.
- **Four exceptions move to the SharedKernel**, because every module needs them: `ObjectNotFoundException`, `ConflictException`, `TooManyRequestsException`, `CaptchaRequiredException`. The three connection exceptions stay in `MDBNavigator.Domain` until 0.7e gives them a home.
- **`SessionKey` moves to the SharedKernel**: the API, the hub and every module build or read session ids.
- **Request and handler names and folders stay as they are** (`ExecuteQueryQuery` included). They are sorted out when the modules are created (0.7e, 0.7f).
- **Code style is this repository's, not What2Eat's:** block-scoped namespaces, constructors with readonly fields, `//` comments.

### Messaging (namespace `MDBNavigator.SharedKernel.Messaging`)

```csharp
// A request that changes state and returns no value.
public interface ICommand { }

// A request that changes state and returns TResponse.
public interface ICommand<TResponse> { }

// A request that only reads state.
public interface IQuery<TResponse> { }

public interface ICommandHandler<in TCommand> where TCommand : ICommand
{
    Task Handle(TCommand command, CancellationToken cancellationToken);
}

public interface ICommandHandler<in TCommand, TResponse> where TCommand : ICommand<TResponse>
{
    Task<TResponse> Handle(TCommand command, CancellationToken cancellationToken);
}

public interface IQueryHandler<in TQuery, TResponse> where TQuery : IQuery<TResponse>
{
    Task<TResponse> Handle(TQuery query, CancellationToken cancellationToken);
}
```

### Decorators (namespace `MDBNavigator.SharedKernel.Behaviors`, both `internal static`)

`LoggingDecorator`: three nested classes as in What2Eat. Each measures the inner call with `Stopwatch.GetTimestamp()` / `Stopwatch.GetElapsedTime()` and, after it returned, logs at Information:

```
{RequestName} handled in {ElapsedMs} ms
```

`RequestName` is `typeof(TCommand).Name` (or `TQuery`). Nothing is logged when the inner call throws; the exception passes through. Class comment: `// Logs the request type and its duration. Never the request itself: it can hold a database password.` Use a `[LoggerMessage]` partial method, as What2Eat does.

`ValidationDecorator`: three nested classes as in What2Eat. Each runs every `IValidator<TRequest>` for the request; when there is at least one failure it throws `new ValidationException(failures)` and the handler is not called; otherwise it calls the handler. With no validators registered it goes straight to the handler.

### `DependencyInjection` (namespace `MDBNavigator.SharedKernel`)

```csharp
public static class DependencyInjection
{
    // Registers every handler and validator of the assembly. Each module calls it for its own assembly; the
    // decorators are added once for all of them by AddHandlerDecorators.
    public static IServiceCollection AddHandlersFromAssembly(this IServiceCollection services, Assembly assembly);

    // Wraps every registered handler. Call once, after all modules are registered.
    // An action that takes a handler receives: logging, then validation, then the handler.
    public static IServiceCollection AddHandlerDecorators(this IServiceCollection services);
}
```

Bodies as in What2Eat's file, including `AddValidatorsFromAssembly(assembly, includeInternalTypes: true)`, scoped handler registrations, and the order in `AddHandlerDecorators` (validation applied first, logging last, so logging is outermost).

`ConnectionRequestHandler<TRequest, TResponse>`:

```csharp
public abstract class ConnectionRequestHandler<TRequest, TResponse> : IQueryHandler<TRequest, TResponse>
    where TRequest : IQuery<TResponse>, IConnectionRequest
```

Its public `Handle(TRequest request, CancellationToken cancellationToken)` and the abstract method stay as they are after 0.7c.

Every handler, by the rule below. Bodies do not change, except the four that returned `Unit`.

| Request declared as | Handler declared as | `Handle` returns |
|---|---|---|
| `ICommand<T>` (T not `Unit`) | `ICommandHandler<TheCommand, T>` | `Task<T>` |
| `ICommand<Unit>`, which becomes `ICommand` | `ICommandHandler<TheCommand>` | `Task`; `return Unit.Value;` becomes `return;` (or the statement is dropped), `return Task.FromResult(Unit.Value);` becomes `return Task.CompletedTask;` |
| `IQuery<T>` | `IQueryHandler<TheQuery, T>` | `Task<T>` |

The four `ICommand` commands: `DisconnectCommand`, `CancelQueryCommand`, `DeleteSavedConnectionCommand`, `ForgetSavedPasswordCommand`.

The 18 handlers that derive from `ConnectionRequestHandler` change only their `using` lines.

`using MediatR;` goes everywhere; `using MDBNavigator.Application.Messaging;` becomes `using MDBNavigator.SharedKernel.Messaging;`.

### Controllers

No `IMediator` field and no constructor for it. Each action takes its handler as the parameter before `CancellationToken`, marked `[FromServices]`, and calls `handler.Handle(request, cancellationToken)`. Routes, attributes, other parameters, status codes and the request built from them stay exactly as they are. Example:

```csharp
[HttpGet("tables/{connectionId}")]
public async Task<IActionResult> Tables(string connectionId, [FromQuery] string database,
    [FromServices] IQueryHandler<GetTablesQuery, TablesDetailsDto> handler, CancellationToken cancellationToken)
    => Ok(await handler.Handle(new GetTablesQuery(SessionId, connectionId, database), cancellationToken));
```

For a command without a value:

```csharp
[HttpPost("cancel/{executionId}")]
public async Task<IActionResult> Cancel(string executionId,
    [FromServices] ICommandHandler<CancelQueryCommand> handler, CancellationToken cancellationToken)
{
    await handler.Handle(new CancelQueryCommand(SessionId, executionId), cancellationToken);
    return NoContent();
}
```

The handler's two type arguments are the request type and the response type the request declares. The controllers need `using` lines for the response DTOs they now name.

## 6. Edge cases & don'ts

- **Don't change what a handler does.** Bodies stay; only the interface, the return of the four value-less commands, and `using` lines change.
- **Don't rename requests, handlers or folders**, and don't merge the script handlers. That belongs to 0.7e and 0.7f.
- **Don't introduce a dispatcher** (`ISender`, `IMediator`, a `Send` helper), and don't put handlers into controller constructors.
- **Don't touch the smoke tests.** If one fails, the change is wrong. If you are sure a test is wrong, stop and ask.
- **`ValidationException` must still be `FluentValidation.ValidationException`**: the middleware matches on it and `RememberedPassword` throws it directly.
- **`ExecuteQueryHandler` resolves `ILogger<ExecuteQueryHandler>` and other services from the queue's scope.** Leave that as it is; it is redesigned in 0.7f.
- **Every closed handler interface must have exactly one registration**, or an action gets the wrong handler. `AddHandlersFromAssembly` skips abstract classes, so `ConnectionRequestHandler` itself is not registered.
- **A handler that is not registered fails only at the first request to its action.** The smoke tests reach every controller action except `Reconnect`'s failure paths; after the change, check by grep that the number of handler classes equals the number of `[FromServices]` handler parameters (29).
- **`MediatR` must be gone completely**: no package reference, no `using`, no mention in `Directory.Packages.props`. Older plans in `docs/plans/` keep their text.
- **The SharedKernel references no other project**, and only the three packages above.
- **`AddHandlerDecorators` is called once**, in `Program.cs`, after all registrations that add handlers. Calling it twice would wrap handlers twice.

## 7. Steps

Each step ends in a state that builds (`dotnet build MDBNavigator.slnx -c Release`, 0 warnings).

1. **The SharedKernel project** with messaging, decorators and `DependencyInjection`, added to the solution and referenced from `Application`. The new `ICommand`/`IQuery` live beside MediatR for the moment: to keep this step building, leave `Application/Messaging` untouched until step 2 and create the SharedKernel interfaces as new files. Build.
2. **Switch the handlers:** request records and handlers to the SharedKernel interfaces, `ConnectionRequestHandler`, `ApplicationServiceRegistration`, `Program.cs`, the four controllers. Delete `Application/Messaging` and `Application/Behaviors`, remove the MediatR package reference and its version line. (Here `git mv` is not worth it for `ICommand.cs` and `IQuery.cs`: delete the old files, the new ones exist.) Build, run both test projects.
3. **Move `SessionKey` and the four exceptions** to the SharedKernel with `git mv`, fix namespaces and `using` lines. Build, run both test projects.
4. **Docs:** `README.md`, `docs/ROADMAP.md`, `CLAUDE.md`.
5. **Verification** (section 8), then the usual summary, what was verified, and a commit message. Don't commit.

Suggested commit message: `Own handler interfaces in a SharedKernel; MediatR removed (roadmap 0.7d)`
