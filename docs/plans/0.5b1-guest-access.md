# 0.5b1 Guest access

## 1. Goal

Invited people try the public demo without an account: an invite link opens a form (name, email, demo terms), an emailed link starts a 10-minute guest session that is already connected to the sample database, and the guest is signed out and deleted when the time is up. Returning visitors get a new link by email.

Roadmap 0.5b (first half; violations and blocks are 0.5b2). Changes README "Configuration" and "Public demo setup", `docs/api.md` "Endpoints", `docs/security.md` "Public demo", `docs/specs/authentication.md` (new "Demo guests" section), `docs/ROADMAP.md` 0.5b row, `compose.demo.yaml`, `.env.example`, CI.

## 2. Decisions

Agreed with the owner on 2026-11-20:

- Invite-only through a secret code in the link (`/demo?code=…`), changed in the settings to stop old links.
- The form asks for a name, an email and agreement to the demo terms (text approved as drafted), plus the CAPTCHA when one is configured. ALTCHA in the demo Compose file.
- An emailed link, valid 30 minutes and usable once, starts the session. The page it opens has a Start button, so a mail scanner that opens the link uses nothing and the 10 minutes start when the visitor is ready.
- One throwaway Identity account per session (role `Guest`), plus a separate visitor list. Nothing from one session survives into the next.
- 10-minute sessions (setting), a countdown in the top bar, then signed out; the account and everything it had are deleted through the same `IUserDataEraser`s as account deletion.
- Returning visitors ask for a link with their email. Unknown emails get the same answer, but no email.
- Limits: 3 sessions per visitor per day, 10 guests at once, 3 new sessions per IP address per hour, 3 link emails per address per hour. All settings.
- Guests have no account page and no Identity `manage/*` endpoints. They may save connections (deleted with the session).
- Email to the owner when a visitor confirms their email for the first time (name and email in the email; never in logs).
- The visitor list (name, email, terms version and time, visits) is deleted 90 days after the last visit. The 90 days is in the terms text, so it is a constant, not a setting.
- `Demo:Enabled` is off by default; with it on, startup requires `Auth:Mode = Accounts`, working email and every demo setting.

My calls inside this plan (reported to the owner with the summary):

- **A visitor exists only once their email is confirmed.** The form's name and terms travel with the link and are written when the link is used, so nobody can put a name on someone else's email, and the list holds only confirmed addresses.
- **The terms version is checked:** the UI sends the version it showed, the server refuses another one ("reload the page"). `DemoTerms.Version` ↔ `DEMO_TERMS_VERSION` join the values kept in sync.
- **The server connects the guest itself** (`POST /api/demo/connect`): `demo_reader`'s password never reaches the browser, and a guest can't point the connection elsewhere.
- **Link requests per IP address:** 10 per hour (`Demo:LinkRequestsPerIpPerHour`), on top of the CAPTCHA, so one address can't send mail to many.
- **A failed start doesn't use the link:** the limits are checked before the link is marked used, so "the demo is full" can be retried with the same link.
- **Guest sessions are checked on every request** (one indexed SQLite lookup, guests only): a session that ended early (Log out now, 0.5b2's blocks later) stops at once, not when the cookie expires.
- **Clean-up runs whether or not the demo is on**, so switching the demo off still deletes visitors after 90 days, as the terms promise.
- **`IEmailDelivery` becomes public**, so the API tests can replace it and read the links.

## 5. Contracts

### Settings (`Demo`)

| Key | Default | Notes |
|---|---|---|
| `Enabled` | `false` | |
| `InviteCode` | `""` | Secret, at least 16 characters. Environment variable or user secrets. |
| `OwnerEmail` | `""` | Gets "new visitor" emails. |
| `ContactEmail` | `""` | Shown in the terms. |
| `SessionMinutes` | `10` | 1–120. |
| `SessionsPerVisitorPerDay` | `3` | Rolling 24 hours. |
| `MaxActiveGuests` | `10` | |
| `SessionsPerIpPerHour` | `3` | Successful starts only. |
| `LinkEmailsPerAddressPerHour` | `3` | Above it, no email (same answer). |
| `LinkRequestsPerIpPerHour` | `10` | Rate limit on both link endpoints. |
| `LinkValidMinutes` | `30` | |
| `Connection:Name` | `"Sample database"` | The connection's name in the UI. |
| `Connection:ServerName`, `Port` (5432), `UserName`, `Password`, `DatabaseName` | `""` | All required. PostgreSQL only. Never sent to the browser. |

With `Enabled`, startup throws `InvalidOperationException` when: `Auth:Mode` isn't `Accounts`; `Email:Delivery` is `None`; `InviteCode` is shorter than 16; `OwnerEmail` or `ContactEmail` isn't an email; a connection value is empty; `SessionMinutes` is outside 1–120; any count is below 1.

### Data (`AccountsDbContext`, migration `AddDemoGuests`)

- `demo_visitors`: `id` (Guid v7), `name` (≤100), `email` (≤256), `normalized_email` (unique), `terms_version` (≤20), `terms_accepted_at_utc`, `created_at_utc`, `last_visit_at_utc`, `visit_count`.
- `demo_sign_in_links`: `id`, `token_hash` (SHA-256, hex, unique), `email`, `normalized_email`, `name` (null for a returning visitor's link), `terms_version`, `created_at_utc`, `expires_at_utc`, `used_at_utc` (null). Index (`normalized_email`, `created_at_utc`).
- `demo_guest_sessions`: `id`, `visitor_id` (FK, cascade), `user_id` (unique, no FK: the row outlives the account for the daily count), `started_at_utc`, `ends_at_utc` (index).

All times `DateTime` UTC from `TimeProvider`.

### Endpoints

All under `/api/demo`, mapped only with `Demo:Enabled` (otherwise 404).

| Route | Body | Answers |
|---|---|---|
| `POST join` | `{ inviteCode, name, email, termsVersion }`, `Captcha-Token` header | 204 (email sent, or not because of the address limit); 403 wrong code; 428 CAPTCHA; 400 validation problem (`InvalidName`, `InvalidEmail`, `TermsChanged`); 429 |
| `POST sign-in-link` | `{ email, termsVersion }`, `Captcha-Token` | 204 whether or not the email is known; 428; 400; 429 |
| `POST start` | `{ token }` | 204 and the session cookie; 400 link invalid; 429 with a message (daily, full, address) |
| `POST connect` | none; `id` header | 200 `ConnectedResultDto`; 401; 403 not a guest |

- `join` and `sign-in-link`: rate limit `DemoLink` (per IP, `LinkRequestsPerIpPerHour` per hour). `start`: `Auth` (per IP per minute). `connect`: `Connect`.
- Invite code compared with `CryptographicOperations.FixedTimeEquals` on UTF-8 bytes.
- Name: trimmed, 1–100 characters, no control characters. Email: trimmed, ≤256, `EmailAddressAttribute`. Terms: equal to `DemoTerms.Version`.
- Messages: wrong code "This invite link isn't valid. Please ask for a new one."; link "This link has expired or was already used. Please ask for a new one."; daily "You have used today's {n} demo sessions. Please come back tomorrow."; full "The demo is full right now. Please try again in a few minutes."; address "Too many demo sessions were started from your network in the last hour. Please try again later."; terms "The demo terms have changed. Please reload the page."

### Changed responses

- `GET /api/auth/settings`: `demo: { contactEmail, sessionMinutes, connectionName } | null`.
- `GET /api/auth/me`: `guest: { name, endsAtUtc } | null`.
- `POST /api/auth/logout`: for a guest, also ends the session and deletes the account at once.
- `/api/auth/account/*` and `/api/auth/manage/*`: 403 for guests, "Demo sessions have no account settings."

### Session

- Guest user: `UserName = "guest-{id:N}"`, `Email = "guest-{id:N}@guest.invalid"`, `EmailConfirmed = true`, no password, role `Guest`. User, role and session row in one transaction.
- `SignInManager.SignInAsync(user, new AuthenticationProperties { IsPersistent = true, ExpiresUtc = endsAt, AllowRefresh = false })`.
- Cookie `OnValidatePrincipal`: Identity's handler first, then for principals in role `Guest`: no session row with `ends_at_utc > now` → `RejectPrincipal` and sign out.
- Link token: 32 random bytes, base64url; link `{Email:AppBaseUrl}/demo/start?token=…`.

### Clean-up (every minute and at startup; one run at a time)

1. Accounts in role `Guest` without a session row, or whose session has ended: erasers, then delete the account.
2. Links created over a day ago.
3. Session rows that ended over two days ago.
4. Visitors whose last visit is over `DemoTerms.VisitorRetentionDays` ago (their sessions go with them).

Logged with counts only.

### Emails

- Link: subject "Your MDBNavigator demo link"; "Here is your link to the MDBNavigator demo. It works once, within {LinkValidMinutes} minutes. Your {SessionMinutes}-minute session starts when you press Start on the page it opens."; button "Open the demo"; "If you didn't ask for this, you can ignore this email."
- Owner: subject "New MDBNavigator demo visitor"; "{name} ({email}) confirmed their email and started a first demo session."

### UI

- Routes (only when `settings.demo`): `/demo` (form; without `?code` it says the demo is invite-only), `/demo/sign-in`, `/demo/check-inbox`, `/demo/start?token=`, `/demo/ended`.
- `DEMO_TERMS_VERSION = '2026-11-20'`; text as approved, with `settings.demo.contactEmail`.
- Top bar for guests: "Demo · 7 min left" (under a minute: "Demo · 0:45 left"); menu shows the name and "End the demo" (no Account).
- At zero, on Log out and on a 401: logout, then a full load of `/demo/ended`.
- A guest's workspace connects through `POST /api/demo/connect` instead of showing the connect dialog; if that fails, the dialog shows as usual.

## 6. Edge cases & don'ts

- Never log names, emails or tokens. Store only the token's hash.
- Don't create the visitor at the form: only when the link is used.
- Check the limits before marking the link used; mark it used with a conditional update (`used_at_utc is null`), so two clicks can't both start.
- The start gate (one start at a time) covers the "at once" count and the IP count; without it, two starts could make 11.
- Unknown email on `sign-in-link`: same 204, no email, no different timing work worth hiding (the email is sent in the request either way; acceptable).
- Don't send the demo connection's password to the UI; don't add it to `me` or settings.
- Don't scan SQL (owner's decision).
- `Email:Delivery = Log` stays Development-only; tests replace `IEmailDelivery` instead.
- Don't change existing API test classes; extend the fixture through virtual members.
- No new project or project reference.

## Changed while building

- **Emails go out after the answer** (`Task.Run`), not within the request: otherwise a returning visitor's request would take longer for a known address than for an unknown one, and the timing would tell who has visited. The tests wait for the email.
- **`me` returns `secondsLeft`** next to `endsAtUtc`, and the countdown counts from it: a browser whose clock is fast would otherwise end the session early.
- **`endsAtUtc` is marked UTC** when read back: SQLite returns times without their kind, and the JSON then lacked the `Z`, so a browser read it as local time. Found by the test.
- **A fourth validation code, `TermsNotAccepted`**, for a request without a terms version.
- **UI files:** the version constant is in `demoTermsVersion.ts` (`demoTerms.ts` clashed with `DemoTerms.tsx` on Windows); both forms share `DemoLinkForm.tsx`; the demo pages map their own error codes in `demoErrors.ts`, so `authErrors.ts` is unchanged; `DatabaseConnectingAction.payload` may be `null` (the guest's connection has no settings in the browser).
- **The connection's server, user and database do reach the browser** in the connect result, like any connect (the UI shows them and needs them to reconnect); only the password stays on the server. The docs say so.
- **The rate-limit message** says minutes once the wait is two minutes or more (the hourly demo limit could otherwise say "3599 seconds").
