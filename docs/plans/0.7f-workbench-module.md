# 0.7f Workbench module

## 1. Goal

What is left of the old core becomes the Workbench module, `src/Modules/Workbench`, with a `Core` and an `Infrastructure` project: the schema tree, script generation, and running and cancelling queries. The query run stops being a 100-line lambda that fetches its own services and becomes a class, `QueryExecution`, with a typed queue in front of it. The twelve pass-through script handlers become one. `MDBNavigator.Application` and `MDBNavigator.Infrastructure` are empty afterwards and are removed; the CAPTCHA code and the request-rate options, which belong to neither module, move to the API.

Roadmap step **0.7f** ([ROADMAP.md](../ROADMAP.md), "0.7 Modular structure"). No behavior change: the same endpoints, status codes, JSON and hub messages. The smoke tests of 0.7b must pass without any change to them.

Docs it changes: `README.md` ("Repository layout"), `docs/ROADMAP.md` (plan link), one UI comment, the owner's local `CLAUDE.md` (nothing but checked).

## 2. Decisions

- **Two projects:** `MDBNavigator.Workbench.Core` (root namespace `MDBNavigator.Workbench`, folder `Application/` with `Schema/`, `Scripts/` and `Queries/`) and `MDBNavigator.Workbench.Infrastructure` (the query queue and its workers, the execution registry, the SignalR hub and notifier). No `Contracts` project: no other module uses the workbench.
- **The workbench reaches connections only through `Connections.Contracts`** (`IDatabaseConnector`, the connection exceptions, `IConnectionClosedListener`).
- **One script use case instead of twelve.** `GetScriptQuery` names the kind of script (`ScriptKind`) and one handler picks the generator method. The twelve routes stay exactly as they are; only what the controller builds changes. Twelve folders with a 15-line pass-through each said nothing that one switch doesn't say better.
- **The query run is a class.** `QueryExecution.RunAsync` holds what the queued lambda did, with its services injected. The queue becomes typed (`IQueryRunQueue` carries a `QueuedQueryRun`), and the worker resolves `QueryExecution` from its own scope. Nothing in Core asks a service provider for anything any more, and the run can be tested with a fake notifier and connector.
- **"Execute query" is a command**, and is named like one: `RunQueryCommand`, `RunQueryCommandHandler`, `RunQueryCommandValidator` (they were `ExecuteQueryQuery`, `ExecuteQueryHandler`, `ExecuteQueryValidator`). The route and the request body don't change.
- **`MaxRunningQueriesPerUser` gets its own options class in the module** (`QueryLimitOptions`, bound to the same `RateLimiting` section), as the failed-connect settings did in 0.7e. The setting name doesn't change.
- **The CAPTCHA implementations and `CaptchaOptions` move to the API** (`src/MDBNavigator.API/Captcha/`), next to the CAPTCHA endpoint, the rate limits and the security headers: cross-cutting web concerns that no module owns. `ICaptchaVerifier` is already in the SharedKernel.
- **`RateLimitingOptions` moves to the API** (`src/MDBNavigator.API/RateLimiting/`) with the three per-minute settings that the API's policies use.
- **Class names of the queue change with their job:** `BackgroundTaskQueue` becomes `QueryRunQueue`, `BackgroundQueueHostedService` becomes `QueryRunHostedService`. The registry, the hub and the notifier keep their names.

### Queries

```csharp
namespace MDBNavigator.Workbench.Application.Queries
{
    // The RateLimiting setting that belongs to running queries. The API's own rate limits read the same section.
    public class QueryLimitOptions
    {
        public const string SectionName = "RateLimiting";

        // (the comment that is on RateLimitingOptions.MaxRunningQueriesPerUser today)
        public int MaxRunningQueriesPerUser { get; set; } = 3;
    }

    // A run that waits for a worker: what to run, and the handle that cancels it (already in the registry).
    public sealed record QueuedQueryRun(RunQueryCommand Command, CancellationTokenSource Cancellation);

    public interface IQueryRunQueue
    {
        void Enqueue(QueuedQueryRun run);

        // Waits until a run is available.
        Task<QueuedQueryRun> DequeueAsync(CancellationToken cancellationToken);
    }

    // One run of a script, on a worker and in the worker's own scope: opens the database, streams the result to the
    // browser, and always ends with exactly one CommandFinished message.
    public class QueryExecution
    {
        public QueryExecution(IDatabaseConnector connector, IBatchNotifier notifier, ICommandExecutionRegistry registry,
            QueryExecutionOptions options, ILogger<QueryExecution> logger, IDatabaseErrorDescriber? errorDescriber = null);

        // stoppingToken: the application is shutting down. cancellation: the user's Cancel, or a disconnect.
        public Task RunAsync(RunQueryCommand command, CancellationTokenSource cancellation, CancellationToken stoppingToken);
    }
}
```

`QueryExecution.RunAsync` is the body of the lambda in today's `ExecuteQueryHandler`, moved as it is: the linked token source, the stopwatch, the `try` with the four `catch` blocks and their comments, the `finally` that completes the registration, and the final `SendCommandFinished`. Only where its services come from changes (fields instead of `services.GetRequiredService`), and `request` becomes `command`. The private helpers `ToDto` and `AtStatement` move with it. The describer stays optional: `_errorDescriber?.Describe(ex) ?? ex.Message`.

## 6. Edge cases & don'ts

- **Don't touch the smoke tests.** `ScriptTests` covers all twelve script routes and `QueryTests` covers the run, the failure texts, cancel and the per-user cap.
- **The run's behavior stays to the letter:** registered before it is queued, so it can be cancelled while it waits; exactly one `CommandFinished`; "Cancelled" for any exception once cancellation was requested; `Statement n of m (line l): ...` only for scripts with more than one statement; the registration completed in `finally`.
- **Workbench.Core must not reference `Connections.Core` or any Infrastructure project**, and must not use ASP.NET Core, SignalR or `IServiceProvider`. `Microsoft.Extensions.Logging.Abstractions` reaches it through the SharedKernel.
- **`QueryExecution` is scoped and is resolved by the worker from the worker's scope.** Don't inject it into the handler, and don't make it a singleton: the notifier and the connector are scoped.
- **Don't change routes, parameters or status codes of the controllers.** Only the handler parameter and the request they build.
- **Messages stay word for word**, including the validator's and the "You already have ... running" text.
- **Setting names don't change** (`QueryExecution:*`, `RateLimiting:*`, `Captcha:*`).
- **The CAPTCHA classes keep their behavior and their names**; only namespace and folder change. `AddCaptcha` keeps its startup checks.
- **Hub method names and the hub path don't change** (`StatementStarted`, `BatchCommandResult`, `CommandFinished`, `/batchCommandResult`).
- **Delete `bin/` and `obj/` of the two old projects**, and remove each project only when `git ls-files` shows nothing but its project file.
- **Don't rename `MDBNavigator.Infrastructure.Accounts`** (0.7g).

## 7. Steps

Each step ends in a state that builds (`dotnet build MDBNavigator.slnx -c Release`, 0 warnings). Run both test projects at the end of steps 2 to 4.

1. **Core project, schema part:** the project, `ConnectionRequestHandler`, the schema DTOs and the six schema handlers; `AddWorkbenchCore` registering handlers. The API references it for now, and `Program.cs` calls `AddWorkbenchCore()` next to `AddApplicationServices()`.
2. **Scripts:** `ScriptKind`, `GetScriptQuery`, `GetScriptHandler`; the controller's twelve actions; delete the twelve old handler folders.
3. **Queries:** move the DTOs, options and interfaces; `IQueryRunQueue`, `QueryExecution`, the `RunQuery` and `CancelQuery` use cases, `QueryLimitOptions`. The Infrastructure project with queue, hosted service, registry, cleanup, hub, notifier and `WorkbenchModule`. `Program.cs` calls `AddWorkbenchModule`; the API references `Workbench.Infrastructure`.
4. **The leftovers:** CAPTCHA code and `CaptchaOptions` to the API, `RateLimitingOptions` to the API; delete `MDBNavigator.Application` and `MDBNavigator.Infrastructure`; solution file.
5. **Docs and the UI comment.** In `mdb-navigator-ui`: `npm run check`, `npm test`, `npm run build`.
6. **Verification** (section 8), then the usual summary, what was verified, and a commit message. Don't commit.
