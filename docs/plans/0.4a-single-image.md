# 0.4a Single image

## 1. Goal

One Docker image that runs the whole app: the API with the built UI inside it, from one multi-stage `Dockerfile` at the repository root. It replaces the two old Dockerfiles and the old `docker-compose.yml`, which no longer work. Two things an image behind a reverse proxy needs come with it: a setting for which proxies are trusted to say who the visitor is, and a health endpoint.

Roadmap step **0.4a** ([ROADMAP.md](../ROADMAP.md), "0.4 Docker"). The Compose setup with PostgreSQL is 0.4b; CI is 0.4c.

Docs it changes: `README.md` ("Production build", the settings table, a new "Docker" section in place of the old one, "Rate limits and CAPTCHA" gets one sentence), `docs/ROADMAP.md` (plan link), the owner's local `CLAUDE.md` (a Docker bullet).

## 2. Decisions

Agreed with the owner on 2026-11-15, or following from it:

- **The image is not published anywhere.** It is built locally (and by CI in 0.4c, without a push). Publishing can be added later.
- **Three stages:** `node:22-alpine` builds the UI, `mcr.microsoft.com/dotnet/sdk:10.0` publishes the API with the UI copied into `wwwroot`, `mcr.microsoft.com/dotnet/aspnet:10.0` runs it. Only the last one is in the image.
- **It runs as the non-root user the .NET images provide** (`$APP_UID`), listens on plain HTTP port **8080**, and keeps its SQLite database in **`/app/data`**, which is a volume. TLS belongs to the proxy in front.
- **No `HEALTHCHECK` instruction in the image:** the runtime image has no `curl` or `wget`, and installing one only for that isn't worth it. The proxy (Caddy in 0.5) and an uptime monitor call the health endpoint from outside.
- **Trusted proxies are a setting, `ReverseProxy:TrustedNetworks`:** a list of IP addresses or CIDR ranges whose `X-Forwarded-For` and `X-Forwarded-Proto` are believed. Empty by default, which keeps today's behavior (only a proxy on the same machine is trusted). Without it, behind a proxy in another container every visitor has the proxy's address (so they share one rate limit) and the app thinks every request is plain HTTP (so HSTS is never sent). Trusting everyone instead would let any client fake its address.
- **A bad entry stops the app at startup**, like a bad `ConnectionGuard:Allow` entry does.
- **Only one proxy hop is read** (ASP.NET Core's default `ForwardLimit` of 1). Two proxies in a row (Cloudflare in front of Caddy) is a question for 0.5c.
- **Health endpoint `GET /health`,** anonymous, outside `/api`: `200` with `Healthy` when both database contexts can reach the SQLite file, `503` otherwise. Each module registers its own check, as What2Eat's modules do. It says nothing about any PostgreSQL server: those are the users' servers, not the app's.
- **`Auth:Mode = None` is not for containers.** It serves only requests from the same machine, and a browser outside the container is not that. The README says so; the image keeps the default, `Accounts`.

## 5. Contracts

### `Dockerfile`

```dockerfile
# syntax=docker/dockerfile:1

# The whole app in one image: the API serves the built UI, so the browser talks to one origin.
# Build from the repository root:  docker build -t mdbnavigator:local .

# 1. The UI
FROM node:22-alpine AS ui
WORKDIR /ui
COPY mdb-navigator-ui/package.json mdb-navigator-ui/package-lock.json ./
RUN npm ci
COPY mdb-navigator-ui/ ./
# Bundling Monaco needs more memory than Node's default heap.
ENV NODE_OPTIONS=--max-old-space-size=4096
RUN npm run build

# 2. The API, with the UI in wwwroot
FROM mcr.microsoft.com/dotnet/sdk:10.0 AS build
WORKDIR /repo
COPY global.json Directory.Build.props Directory.Packages.props ./
COPY src/ src/
# The NuGet cache is kept between builds; it is not part of any layer.
RUN --mount=type=cache,target=/root/.nuget/packages \
    dotnet publish src/MDBNavigator.API/MDBNavigator.API.csproj -c Release -o /app/publish /p:UseAppHost=false
COPY --from=ui /ui/dist/ /app/publish/wwwroot/

# 3. What runs
FROM mcr.microsoft.com/dotnet/aspnet:10.0 AS final
WORKDIR /app
COPY --from=build /app/publish/ ./
# The app's SQLite database (ConnectionStrings:AppDb, data/mdbnavigator.db). Owned by the user the app runs as,
# so a new volume mounted here is writable.
RUN mkdir /app/data && chown $APP_UID /app/data
VOLUME /app/data
# Not root. Plain HTTP on 8080: TLS belongs to the proxy in front.
USER $APP_UID
ENV ASPNETCORE_HTTP_PORTS=8080
EXPOSE 8080
ENTRYPOINT ["dotnet", "MDBNavigator.API.dll"]
```

### Trusted proxies

```csharp
namespace MDBNavigator.API.ReverseProxy
{
    public class ReverseProxyOptions
    {
        public const string SectionName = "ReverseProxy";

        // The proxies in front of the app: IP addresses or ranges such as 172.16.0.0/12. Only their
        // X-Forwarded-For and X-Forwarded-Proto are believed. Empty: only a proxy on this machine (loopback).
        public List<string> TrustedNetworks { get; set; } = [];

        // Each entry as a network; a single address becomes a network of that one address.
        // Throws InvalidOperationException naming the entry when it is neither an address nor a range.
        public static IReadOnlyList<System.Net.IPNetwork> Parse(IEnumerable<string> entries);
    }

    public static class ForwardedHeadersSetup
    {
        // X-Forwarded-For and X-Forwarded-Proto, from loopback and from ReverseProxy:TrustedNetworks only.
        // Logs once which networks are trusted.
        public static IApplicationBuilder UseTrustedForwardedHeaders(this WebApplication app, ReverseProxyOptions options);
    }
}
```

- The error text: `ReverseProxy:TrustedNetworks: '{entry}' is not an IP address or a range like 10.0.0.0/8.`
- Entries are trimmed; empty entries are an error.
- `UseTrustedForwardedHeaders` builds a `ForwardedHeadersOptions` with `ForwardedHeaders.XForwardedProto | ForwardedHeaders.XForwardedFor`, keeps the framework's defaults (loopback trusted, one hop), and adds the parsed networks to the options' list of known networks. Use the property that is not marked obsolete in .NET 10 (the Release build treats the obsolete warning as an error, so the build tells which one; at the time of writing that is `KnownIPNetworks`, which takes `System.Net.IPNetwork`). If no non-obsolete property accepts `System.Net.IPNetwork`, stop and report.
- Log line (Information): `Forwarded headers are trusted from loopback and {Count} configured networks: {Networks}`, or `Forwarded headers are trusted from loopback only` when the list is empty.

`Program.cs`:

- Bind next to the other options: `var reverseProxyOptions = builder.Configuration.GetSection(ReverseProxyOptions.SectionName).Get<ReverseProxyOptions>() ?? new ReverseProxyOptions();`
- Replace the `app.UseForwardedHeaders(new ForwardedHeadersOptions { ... });` block with `app.UseTrustedForwardedHeaders(reverseProxyOptions);`. It stays the first middleware, where it is now.

`appsettings.json`: add after `"AllowedHosts"`:

```json
  "ReverseProxy": {
    "TrustedNetworks": []
  },
```

````
## Docker

One image holds the whole app: the API with the built UI in it.

```sh
docker build -t mdbnavigator:local .
docker run --rm -p 8080:8080 -v mdbnavigator-data:/app/data \
  -e Auth__Admin__Email=you@example.com -e Auth__Admin__Password=change-this-password \

- **HTTPS:** the container speaks plain HTTP on port 8080. Put a reverse proxy with TLS in front of it and set `ReverseProxy__TrustedNetworks__0` to the proxy's address or network. The sign-in cookie is `Secure`, so without HTTPS signing in works only on `http://localhost`.
- **Your databases:** inside the container, `localhost` is the container itself. To reach a PostgreSQL on the Docker host use `host.docker.internal`, and with open sign-up allow it (see [connection guardrails](#connection-guardrails)).
- **Health:** `GET /health` answers `200 Healthy` when the app's own database is reachable, for a proxy or an uptime monitor.
- **`Auth:Mode = None` is not for containers:** it serves only requests from the same machine, and your browser is outside the container.
- The image runs as a non-root user.

A Compose file with PostgreSQL and a sample database follows in roadmap step 0.4b.
````

## 6. Edge cases & don'ts

- **Never put a secret, the owner's database or `.env.development.local` into the image or the build context.** After the build, check the image (section 8).
- **Don't publish or push the image**, and don't log in to any registry.
- **Don't trust all proxies** (no clearing of the known lists, no `ASPNETCORE_FORWARDEDHEADERS_ENABLED`). Only loopback plus the configured networks.
- **The default must behave exactly as today:** with `TrustedNetworks` empty, the forwarded-headers options are the framework's defaults plus the two header flags.
- **`/health` stays anonymous and unlimited**, and must not be caught by the SPA fallback or the controllers' `RequireAuthorization`.
- **The container's test runs use their own volume and ports** (for example host port 18080), are removed afterwards (`docker rm -f`, `docker volume rm`), and never mount `src/MDBNavigator.API/data`. Don't remove or stop containers, images or volumes you did not create: the owner has others (`PostgreSQLDB`, `what2eat-postgres`, old `mdbnavigator-*` ones).
- **Never connect anything to the owner's PostgreSQL** (`PostgreSQLDB`, port 5432).
- **The architecture test must still pass:** the new package goes only into `MDBNavigator.Accounts` and `MDBNavigator.Connections.Infrastructure`, never into a `.Core` or `.Contracts` project.
- **Existing smoke tests are not edited.** Only the two new test files are added.
- **`Dockerfile` and `.dockerignore` use LF line endings.** The `# syntax=` line must be the file's first line.
- **Don't add `curl`, `wget` or a shell script to the runtime image.**
- **The old `docker-compose.yml` is deleted, not fixed.** 0.4b writes the new one.

|---|---|
