# 0.6d: sign-in and account emails from the Gatehouse.Accounts package

## 1. Goal

Replace MDBNavigator's own provider sign-in (Google, Microsoft, GitHub) and the sending of Identity's account emails with the owner's NuGet package `Gatehouse.Accounts` 0.1.0 (nuget.org, MIT). Routes, error codes, email texts and the UI stay the same; one setting is renamed (`Email:AppBaseUrl` becomes `Email:FrontendBaseUrl`).

Roadmap step **0.6d** (new row). Changes README "Configuration" (the `Email:Delivery` row) and the project table, and the authentication spec's Settings table and its "Social login" and "Email" bullets.

## 2. Decisions

**Rules where the package offers a choice: MDBNavigator keeps its own.**

- `UnconfirmedAccountWithSameEmail = Refuse`. An existing account whose email was never confirmed is not linked: `external-email-in-use`, as today. (The package's default, `TakeOver`, is What2Eat's rule.)
- `ConfirmUnverifiedEmailOfNewAccounts` stays `false` (default): a new account through Microsoft has an unconfirmed email, as today.
- `LoginPath` (`/login`) and `CallbackPathPrefix` (`/api/auth/signin-`) keep their defaults: they are MDBNavigator's paths today.

**Routes.**

- `GET /api/auth/external/{provider}` and `/api/auth/external/callback`: the package's default prefix is today's route. `MapExternalSignIn<ApplicationUser>()` is called on `app`, not on the `/api/auth` group, because the package builds the callback address from its own prefix. The returned group gets today's rate limit (`RateLimitPolicies.Auth`).
- `GET /api/auth/providers` is **not mapped**. The UI reads the providers from `GET /api/auth/settings`, which now takes them from the package's `ExternalProviderList`. No frontend change, no new endpoint.
- The account page's `link/{provider}` finds the provider through `ExternalProviderList.Find` too. The rest of linking, unlinking and setting a password stays MDBNavigator's (`AccountManagement`).

**Closed sign-up** (`Auth:SignUp = Closed`) moves into the hook `AllowNewAccountAsync`. Same code as today: `external-sign-up-closed`.

**What changes for users, taken from the package as it is:**

- An account found by its email that is **locked out** is refused (`external-locked-out`). Today it was linked and signed in. The UI has the message already.
- A new account's email is confirmed through `UserManager` instead of by setting the field. Same result.
- A failed send logs only the exception's type name, not the exception (an SMTP answer can hold the address).
- The Development log line of an email also names the sender: `Email (not sent, Development) to … from MDBNavigator <…>: …`.
- **With `Email:Delivery = None`** the package's sender is registered too (today Identity's silent default stays). Each email that would have gone out is one warning in the log, without the address: `Email delivery is None: an email was not sent`. That is one line per sign-up on an instance without email.
- Email settings are checked when the host starts (the package's `ValidateOnStart`), no longer while services are registered. The app still doesn't start with wrong settings. `FrontendBaseUrl` must be `http` or `https`.

**Settings.**

- `Email:AppBaseUrl` becomes `Email:FrontendBaseUrl` (`appsettings.Development.json`, `compose.demo.yaml`, both test fixtures, README, spec). The demo server's `.env` doesn't change: `compose.demo.yaml` builds the value from `MDBNAV_DOMAIN`. The owner's user secrets already have `Email:FrontendBaseUrl`.
- `Email:FromName`: the package's default is empty, MDBNavigator's was `MDBNavigator`. The default moves into `appsettings.json` (`"FromName": "MDBNavigator"`), so every setup keeps the name without setting it.
- `Email:ConfirmEmailPath` and `Email:ResetPasswordPath` exist through the package; their defaults are the UI's pages. Not documented: nobody needs to change them.

**What MDBNavigator gains, and what it uses:**

| Gain | Used? | Why |
|---|---|---|
| Facebook sign-in | No | Not documented, no logo in `ProviderLogo.tsx`. The package has no switch to leave a provider out: someone who sets `Authentication:Facebook` keys gets a working "Continue with Facebook" button without a logo. |
| Disabled-account hook (`CanSignInAsync`) | No | `ApplicationUser` has no disabled flag. `external-disabled` is never sent, so the UI gets no text for it. |
| Provider's display name in `CreateUser` | No | `ApplicationUser` has no name field. |
| Email kind `ConfirmEmailChange` | Handled, same text | Only Identity's `manage/info` can change an email, and the UI has no form for it. The composer sends today's "Confirm your email" text for it, as before. |
| `From` override, extra headers | No | Every email comes from `Email:FromAddress`. |
| `IEmailDelivery` (public) | Yes | The demo's emails (sign-in link, new visitor, block) go through it, as they went through MDBNavigator's own interface. |

**One fix in the same area:** `DemoEmails.SendInBackground` logs the whole exception when a demo email fails. An SMTP answer can hold the recipient's address, and the project's rule is no emails in logs. It now logs the exception's type name only, like the package's sender.

**Packages.** `Gatehouse.Accounts` goes into `MDBNavigator.Accounts`; the API and the API tests get it through the project reference. `MailKit`, `AspNet.Security.OAuth.GitHub`, `Microsoft.AspNetCore.Authentication.Google` and `.MicrosoftAccount` leave the `.csproj` and `Directory.Packages.props`: nothing else uses them, and the package brings them at the same versions (4.18.2, 10.0.0, 10.0.14). New through the package: `Microsoft.AspNetCore.Authentication.Facebook` 10.0.14 (MIT).

**No test of the redirects is added.** The package tests its own rules; this step checks MDBNavigator's wiring with curl (section 8).

### Emails

`Accounts/Email/AccountEmailComposer.cs`:

```csharp
using Gatehouse.Accounts;
using MDBNavigator.Accounts.Identity;

namespace MDBNavigator.Accounts.Email
{
    // Writes the account emails Gatehouse.Accounts sends. The package decides which email is needed and builds its link
    // to the UI page (/confirm-email, /reset-password under Email:FrontendBaseUrl); the texts and the design are ours.
    internal sealed class AccountEmailComposer : IAccountEmailComposer<ApplicationUser>
    {
        public Task<EmailMessage?> ComposeAsync(ApplicationUser user, AccountEmail email, CancellationToken ct)
            => Task.FromResult<EmailMessage?>(email.Kind switch
            {
                // A changed email (Identity's manage/info; the UI has no form for it) gets the same text as a new account's.
                AccountEmailKind.ConfirmEmail or AccountEmailKind.ConfirmEmailChange => EmailTemplates.ConfirmEmail(email.To, email.Link),
                AccountEmailKind.ResetPassword => EmailTemplates.ResetPassword(email.To, email.Link),
                // The package's sender catches it and logs the kind: better than the wrong text for a kind added later.
                _ => throw new ArgumentOutOfRangeException(nameof(email), email.Kind, "Unknown account email kind.")
            });
    }
}
```

### Sign-in

`Accounts/Identity/AppExternalAccountHooks.cs`:

```csharp
using Gatehouse.Accounts;

namespace MDBNavigator.Accounts.Identity
{
    // MDBNavigator's part of provider sign-in. The rules (find, link or create the account) are Gatehouse.Accounts'.
    internal sealed class AppExternalAccountHooks : ExternalAccountHooks<ApplicationUser>
    {
        private readonly AuthOptions _options;

        public AppExternalAccountHooks(AuthOptions options)
        {
            _options = options;
        }

        // The package saves the user and confirms the email, only when the provider verified it.
        public override ApplicationUser CreateUser(ExternalAccount account)
            => new() { UserName = account.Email, Email = account.Email };

        // Closed sign-up: existing accounts can still sign in through a provider, new ones aren't created.
        public override ValueTask<bool> AllowNewAccountAsync(ExternalAccount account, CancellationToken ct)
            => ValueTask.FromResult(_options.SignUp == SignUpMode.Open);
    }
}
```

## 6. Edge cases & don'ts

- **Never change anything in `C:\Projects\Pro\Gatehouse` or `C:\Projects\Pro\What2Eat`.** If the package is wrong or missing something, stop and report.
- **Never log** an email address, a name, a token, a code or a link. Don't print the API's log lines that hold them into the report; say that the line is there.
- **Don't call `MapExternalProviders()`**, and don't call `MapExternalSignIn` on the `/api/auth` group or with a relative prefix: the callback address would be wrong.
- **Don't register `EmailOptions` as a plain singleton** again. Consumers take `IOptions<EmailOptions>`.
- **Don't set `EmailConfirmed`** in `CreateUser`: the package confirms through `UserManager`.
- **Don't add** Facebook docs, a Facebook logo, a text for `external-disabled`, a display name, or a new email text.
- **Don't touch the UI.** `git status` must show nothing under `mdb-navigator-ui`.
- **Type names:** after step 3 `EmailOptions`, `EmailMessage`, `IEmailDelivery`, `EmailDelivery` and `ExternalProviders` exist only in `Gatehouse.Accounts`. A leftover `MDBNavigator.Accounts.Email.EmailOptions` means a delete was missed.
- **Restore:** if it says the package doesn't exist, run `dotnet restore MDBNavigator.slnx --no-http-cache` (NuGet remembers a "not found" for about 30 minutes). No `nuget.config`, no extra source: CI and the Docker build know only nuget.org.
- **The API usually runs from Visual Studio**, which locks `bin/`: build and test with `-o` into the scratch folder. The check copy runs on port 5199; if the port is in use, stop and ask.
- **The owner's user secrets set real SMTP and Google keys.** The check copy runs with `Email__Delivery=Log` and its own SQLite file, never `src/MDBNavigator.API/data`. Register only the one throwaway address of section 8.
- **The auth rate limit is 10 requests a minute per address.** The curl checks stay under it; after a `429`, wait a minute.
- **Never commit, stage or push.**
