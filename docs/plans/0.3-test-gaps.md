# 0.3 Test gaps

## 1. Goal

Close the gaps that are left in roadmap **0.3 Tests** (0.3a–c). Most of 0.3 was built along the way, in 1.3a (Vitest), 1.3e (provider xUnit) and 0.7b (API smoke tests). This step adds what is still missing: the UI's reducers and `batchBuffer`, PostgreSQL identifier quoting and the generated scripts, and the email and lockout flows of sign-in.

Roadmap step **0.3** ([ROADMAP.md](../ROADMAP.md), "0.3 Tests"). Docs it changes: `docs/ROADMAP.md` (the 0.3 rows and the "Order of what is left" line). README already describes the test projects in general terms ("Development", "Repository layout") and needs no change.

**No application code changes.** Only test files, one test fixture, the API tests' sample schema, and the roadmap. If a test seems to need a change to app code, stop and ask.

## 2. Decisions

- **One step, not three.** The gaps add up to roughly S–M, so 0.3a, 0.3b and 0.3c are closed together.
- **The auth context (`AuthContextProvider`) gets no unit tests.** Testing it needs a DOM (`jsdom` and `@testing-library/react`, two new dev dependencies and a second Vitest environment), and what it does is glue: it calls the API and reloads the page. The API side of sign-in is covered by the API tests, including the new email and lockout tests. The roadmap row says so. Vitest stays in Node, for pure functions only, as `vitest.config.ts` says.
- **Reducers are tested as pure functions:** they get a state and an action, and the test checks the returned state. There is no React, and no context provider.
- **`batchBuffer` is tested with Vitest's fake timers** (`vi.useFakeTimers()`) and a `vi.fn()` dispatch.
- **Script generation is tested on two levels.** The scripts built in C# (`DROP …`, `SELECT … LIMIT`, the templates) get provider unit tests, which construct `PostgresScriptGenerator` with an unopened `new NpgsqlConnection()`; those methods never touch the connection. The scripts built by SQL in the database (`CREATE TABLE`, `INSERT`, routine definitions and drops) get API tests against the test container, since only a real PostgreSQL can show they're right.
- **`QuoteIdentifier` stays private.** It is tested through the public methods that use it. Don't make it `internal` or public for the tests.
- **The API tests' sample schema gets three objects:** a schema and a table whose names need quoting, and a second overload of `smoke_add`. Existing tests only look for the old objects by name, so they keep passing.
- **Email flows get their own fixture** (`EmailAppFixture`, its own collection and container), because with email on, password sign-in needs a confirmed email. That would break the main fixture's `NewUserAsync`. Closed sign-up gets one too (`ClosedSignUpAppFixture`). Both follow `LimitsAppFixture`. The extra containers start in parallel with the other collections.
- **`CapturedEmails` and `TestClock` move to a file of their own** (`Infrastructure/CapturedEmails.cs`), unchanged, so `EmailAppFixture` doesn't depend on the demo fixture's file. This is a pure move.

## 5. Contracts

### 5.1 UI test cases

Build test data with small helper functions at the top of each file, such as `batch(overrides)`, `finished(overrides)` and `command(overrides)`, typed with the real model types (`DatabaseCommandBatchResult`, `StatementStartedResult`, `CommandFinishedResult` in `models/databaseCommand/result/`, `ConnectedResult` in `models/connect/`). Each reducer test also checks that **the input state wasn't changed**: take `structuredClone(state)` before the call, and `expect(state).toEqual(copy)` after it.

**`batchBuffer.test.ts`** (`createBatchBuffer`, `FLUSH_INTERVAL_MS` = 150 is not exported, so use 150 in the test with a comment). Put `vi.useFakeTimers()` in `beforeEach` and `vi.useRealTimers()` in `afterEach`.
- `push` doesn't dispatch at once; after `vi.advanceTimersByTime(150)` there is exactly one `RowsAppended` with all pushed batches, in push order.
- Batches pushed while a timer is already running go into the same dispatch: push, advance 100, push, advance 50, and there is one dispatch with both.
- `pushStatement` keeps only the latest message per `executionId`. Two runs each keep their own latest, so two `StatementStarted` dispatches.
- On one flush, `RowsAppended` is dispatched before any `StatementStarted`. Check the order of `dispatch.mock.calls`.
- `flush()` dispatches at once and cancels the timer: advancing 150 afterwards dispatches nothing more.
- `flush()` with nothing queued dispatches nothing.
- After a flush, a new `push` starts a new timer and dispatches again 150 ms later.

**`DatabaseCommandReducer.test.ts`** (`databaseCommandReducer`, `initialDatabaseCommandState`)
- `Executing` for an unknown id adds a command with `isExecuting: true`, the `executionId` and `ranOn`, and empty `resultSets`.
- `Executing` for an existing command keeps its `query`, and clears `resultSets`, `error`, `status`, `stats` and `runningStatement`.
- `Queried` for an unknown id adds a command with that query. For an existing command it sets the query and clears `resultSets` and `error`.
- `RowsAppended`:
  - The first batch of a `resultSetIndex` creates a result set with its `fields`.
  - The rows of several batches in one action are appended in order.
  - `isLastBatch` sets `isComplete`, `truncated` and `skippingRest`.
  - Two result set indexes stay separate.
  - Batches with another `executionId`, from an older run, are ignored and the command object is the same reference (`toBe`).
  - A command whose `executionId` is null ignores them.
  - `isExecuting` stays true.
  - One action with batches of two commands updates both.
- `StatementStarted` sets `runningStatement` `{ index, count }` for the current run only.
- `CommandFinished`:
  - `Completed` sets `isExecuting: false`, `runningStatement: null`, the status and `stats` (all four fields), and `error: null`.
  - `Failed` with an `error` keeps that message. `Failed` without one gives `'Query execution failed'`.
  - A message of an older run changes nothing.
- `CommandRemoved` removes only that command.
- `HubStatusChanged`:
  - `'reconnecting'` and `'disconnected'` turn every executing command with an `executionId` into `Failed` with `'Connection to server lost during execution'`. Use `it.each` over both values.
  - Commands that aren't executing are untouched.
  - `'connected'` changes only `hubStatus`.
- `Error` sets `Failed`, the message and `isExecuting: false` on that command only.
- An unknown action type returns the same state (`toBe`). Cast with `as unknown as DatabaseCommandActions`.

**`CommandQueryReducer.test.ts`**
- `Queried` appends the query and keeps the earlier ones.
- `TreeDatabasePicked` sets `lastTreeDatabase`.
- Picking the same connection and database again returns the same state object (`toBe`). The comment in the reducer says why: no re-render.
- Picking another database of the same connection changes it.

**`DatabaseSchemaReducer.test.ts`** (`databaseSchemaReducer`, `initialDatabaseConnectState`; it uses immer)
- `AddedSchema` adds a schema. Adding the same `connectionId` again leaves one entry.
- `RemovedSchema` removes only that connection's schema.
- `FetchedDatabases` sets `databasesDetails`, and clears that schema's `isLoading` and `error`.
- `FetchedTables`, `FetchedViews`, `FetchedFunctions` and `FetchedStoredProcedures` set the right field on the right database (`it.each`). For a database that isn't in the list nothing changes, apart from `isLoading: false`.
- `FetchedTableDefinition` replaces the entry of the same schema and table, and keeps the other tables' entries.
- `Error`:
  - Scope `Databases` sets `schema.error`, even before any database list arrived. A schema that already has `databasesDetails` keeps them.
  - An error without `connectionId` sets `state.error`.
  - Scope `Tables` sets `tablesError` and clears `tablesDetails` of that database.
  - Scope `TableDefinition` replaces only that table's entry with one that has `tableDefinitionError` and empty `columns`.
  - `Functions`, `Procedures` and `Views` set their `…Error` (`it.each`).
- `ResetTables`, `ResetViews`, `ResetFunctions` and `ResetStoredProcedures` clear their field (`it.each`).
- The returned state is frozen (`Object.isFrozen(next.databaseSchemas![0])`). That is what immer guarantees, and the comment in the reducer relies on it.

For the payload shapes, read `DatabaseSchemaActionTypes.tsx` and the models under `models/schema/`. Keep the builders minimal: empty arrays and only the fields the reducer reads.

**`DatabaseServerConnectReducer.test.ts`** (`databaseConnectReducer`, `initialDatabaseConnectState`)
- `Connecting` sets `isConnecting` and clears `error`, and keeps `connectNewDatabaseServer`. The dialog stays open.
- `Connected`:
  - Adds a connection and closes the dialog flags (`connectNewDatabaseServer`, `reconnectDatabaseServer`, `reconnectDatabaseServerId`), with `captchaRequired: false`.
  - `name` is `display.name`, or `payload.serverName` when that is null.
  - `color` is `display.color` when set, otherwise `pickConnectionColor(...)`. Assert it is one of `CONNECTION_COLORS`. Two connections to the same server get different colors.
- `Reconnected` replaces the connection's `connectedResult` and keeps its `name` and `color`, even when the new result has a different `serverName`.
- `Disconnected` removes only that connection.
- `ConnectNewDatabaseServer`, `PromptReconnectWithSettings` (sets `reconnectDatabaseServerId`) and `ConnectDialogCancelled` set the dialog flags as the reducer does, and clear `error` and `captchaRequired`.
- `Error`:
  - Sets `error` and `isConnecting: false`.
  - `captchaRequired: true` in the action sets it.
  - Once set, a later `Error` without `captchaRequired` keeps it true (sticky).

If `Npgsql` isn't visible in the test project through the provider's project reference, stop and ask. Don't add a package reference on your own.

Cases (exact expected strings):
- `GetDropTableScript("public", "users")` → `DROP TABLE "public"."users";`
- Case and spaces are kept: `GetDropTableScript("Sales Data", "OrderItems")` → `DROP TABLE "Sales Data"."OrderItems";`
- An embedded double quote is doubled: `GetDropTableScript("a\"b", "t")` → `DROP TABLE "a""b"."t";`
- An injection attempt stays one identifier: `GetDropTableScript("public", "x\"; DROP TABLE t; --")` → `DROP TABLE "public"."x""; DROP TABLE t; --";`
- Non-ASCII is kept: `GetDropViewScript("public", "Übersicht")` → `DROP VIEW "public"."Übersicht";`
- Invalid names throw `ArgumentException` with the right `ParamName`: `""`, `"   "`, and `"a\0b"` as schema (`"schema"`) and as table name (`"name"`). Use `[Theory]`, through `GetDropTableScript`.
- `GetTopNTableRecordsScript("public", "t", n)`:
  - `null` → `SELECT * FROM "public"."t"`
  - `-1` → the same, without `LIMIT`
  - `0` → `… LIMIT 0`
  - `1000` → `… LIMIT 1000`
- The templates quote the schema. Assert with `Assert.StartsWith`:
  - `GetCreateStoredProcedureScript("my\"schema")` → `CREATE OR REPLACE PROCEDURE "my""schema".MyProcName(`
  - `GetCreateFunctionScript(...)` → `CREATE OR REPLACE FUNCTION "my""schema".MyFuncName(`
  - `GetCreateViewScript(...)` → `CREATE OR REPLACE VIEW "my""schema".MyView AS`
  - `GetCreateNewTableScript(...)` → `CREATE TABLE "my""schema"."MyTable"`
- Each template throws `ArgumentException` for an empty schema.

### 5.3 API tests: scripts

`AppFixture.SampleSchema`: append, keeping the comment "Read-only for the tests":

```sql
create schema "Smoke ""Quoted""";
create table "Smoke ""Quoted"""."Mixed Case" ("Order Id" int primary key, "Note" text);
create function smoke_add(a text, b text) returns text language sql as 'select a || b';
```

`ScriptQuotingTests.cs`, `[Collection(ApiCollection.Name)]`. A private helper reads a script:

```csharp
// The script endpoints answer with the script as the body. A string result may come as text/plain or as a JSON string.
private async Task<string> ScriptAsync(ApiSession session, string connectionId, string route, string query, HttpStatusCode expected = HttpStatusCode.OK)
```

It GETs `/api/databaseCommand/{route}/{connectionId}?database=postgres&{query}` and checks the status. When the content type is `application/json` it returns `JsonSerializer.Deserialize<string>(body)`, otherwise the body. Normalize `\r\n` to `\n`. Query values go through `Uri.EscapeDataString`.

Schema `Smoke "Quoted"`, table `Mixed Case`. The expected strings are what PostgreSQL's `quote_ident` and the C# code produce:
- `dropTableScript` → exactly `DROP TABLE "Smoke ""Quoted"""."Mixed Case";`
- `createTableScript`:
  - starts with `CREATE TABLE "Smoke ""Quoted"""."Mixed Case" (`
  - contains `"Order Id" integer NOT NULL` and `"Note" text`
  - contains `ALTER TABLE "Smoke ""Quoted"""."Mixed Case" ADD PRIMARY KEY ("Order Id");`
- `insertTableScript` → exactly `INSERT INTO "Smoke ""Quoted"""."Mixed Case" ("Order Id", "Note")\nVALUES (DEFAULT, DEFAULT);`
- `tableRecordsScript` with `recordsNumber=5` → exactly `SELECT * FROM "Smoke ""Quoted"""."Mixed Case" LIMIT 5`
- `dropProcedureScript` for `public.smoke_add` → exactly two lines, in this order (by oid, the int overload was made first):
  `DROP FUNCTION "public"."smoke_add"(a integer, b integer);`
  `DROP FUNCTION "public"."smoke_add"(a text, b text);`
- `dropProcedureScript` for `public.smoke_noop` → `DROP PROCEDURE "public"."smoke_noop"();`
- `procedureDefinition` for `public.smoke_add` contains `CREATE OR REPLACE FUNCTION public.smoke_add(a integer, b integer)` and `CREATE OR REPLACE FUNCTION public.smoke_add(a text, b text)`. These come from `pg_get_functiondef`, which writes `public` without quotes.
- Not found answers 404:
  - `createTableScript` for `public.no_such_table`
  - `insertTableScript` for `public.no_such_table`
  - `procedureDefinition` for `public.no_such_routine`
  - `dropProcedureScript` for `public.no_such_routine`
  - `viewDefinition` for `public.no_such_view`
- An invalid identifier answers 400: `dropTableScript` with `schema=%20` (one space) and `table=t`.

If one of these exact strings differs because of how PostgreSQL 17 formats it (spacing, `integer` against `int4`), check the real output first. Then change the expectation only if the real output is still correctly quoted, and note it under "Changed while building". A real quoting bug is a stop-and-ask.

### 5.4 API tests: email flows

`Infrastructure/EmailAppFixture.cs`:

```csharp
[CollectionDefinition(Name)]
public sealed class EmailCollection : ICollectionFixture<EmailAppFixture>
{
    public const string Name = "API with email";
}

// An app that sends email (caught, not sent): accounts need a confirmed email to sign in with a password, and
// passwords can be reset. A collection of its own: in the main app NewUserAsync signs in right after registering.
public sealed class EmailAppFixture : AppFixture
{
    public const string AppBaseUrl = "https://app.example.test";

    public CapturedEmails Emails { get; } = new();

    public EmailAppFixture() : base(new Dictionary<string, string>
    {
        ["Email:Delivery"] = "Smtp",
        ["Email:Smtp:Host"] = "smtp.invalid",
        ["Email:FromAddress"] = "sender@example.test",
        ["Email:AppBaseUrl"] = AppBaseUrl,
    })
    {
    }

    protected override void ConfigureServices(IServiceCollection services) => services.AddSingleton<IEmailDelivery>(Emails);

    public static string NewEmail() => $"user-{Guid.NewGuid():N}@example.test";

    // The query string values of the first link in the email that starts with AppBaseUrl/path.
    public static Dictionary<string, string> LinkQuery(EmailMessage message, string path) { ... }
}
```

`LinkQuery` finds `AppBaseUrl + "/" + path + "?"` in `message.TextBody` with a regex up to the first whitespace. It parses the query with `Microsoft.AspNetCore.WebUtilities.QueryHelpers.ParseQuery`, which decodes the values, and fails the test with the body in the message when there's no link. The links are built in `src/Modules/Accounts/MDBNavigator.Accounts/Email/IdentityEmailSender.cs`: `/confirm-email?userId=…&code=…` and `/reset-password?email=…&code=…`.

`EmailFlowTests.cs`, `[Collection(EmailCollection.Name)]`, all with anonymous clients (`CreateAnonymousClient`). Each test uses a fresh email:
1. `Settings_say_email_is_on`: `emailEnabled` is true.
2. `Sign_in_waits_for_the_confirmed_email`:
   - register → 200, and a confirmation email arrives (`Emails.WaitForAsync(email)`).
   - Login with `?useCookies=true` → 401.
   - `GET /api/auth/confirmEmail?userId=…&code=…` with the link's values, escaped → 200.
   - Login → 200 (use `SignInAsync`), and `GET /api/auth/me` shows that email.
3. `A_wrong_confirmation_code_is_refused`: register, then `confirmEmail` with the right `userId` and `code=wrong` → 401. That is Identity's answer. If it is something else, check what Identity's `MapIdentityApi` returns and assert that.
4. `The_password_can_be_reset`:
   - Register and confirm, as in 2.
   - `POST /api/auth/forgotPassword` `{ email }` → 200, and a second email arrives (`WaitForAsync(email, 2)`).
   - `POST /api/auth/resetPassword` `{ email, resetCode = link code, newPassword = "a-new-smoke-password" }` → 200.
   - Login with the old password → 401, with the new one → 200.
5. `Forgot_password_for_an_unknown_email_sends_nothing`: `forgotPassword` for a never-registered email → 200 (the same answer as for a real one). After `CapturedEmails.SettleAsync()`, `Emails.To(email)` is empty.
6. `A_wrong_reset_code_is_refused`: register and confirm, then `resetPassword` with `resetCode = "wrong"` → 400. Login with the old password still works.

## 6. Edge cases & don'ts

- **Don't change app code** to make a test pass, and don't change how existing tests behave. A failing test that shows a real bug is a stop-and-ask: report it and leave it failing.
- **Don't touch the owner's PostgreSQL or `src/MDBNavigator.API/data`.** All tests use the container and a temporary SQLite file through the fixtures.
- **No new npm or NuGet packages.** Vitest's `vi` is already there. `Microsoft.AspNetCore.WebUtilities` comes with the API project reference.
- **No `jsdom`, no `.test.tsx`.** `vitest.config.ts` only includes `src/**/*.test.ts` and runs in Node. If importing a reducer pulls in something that needs a browser (`window`, `document`), stop and ask; don't change the config.
- **Don't add the email tests to the main or the demo collection.** Email changes sign-in for everyone in that app.
- **Lockout:** never with the admin account. It would lock the admin for 5 minutes for every other test.
- **The `Smoke "Quoted"` objects are read-only** like the rest of `SampleSchema`. No test may drop or change them.
- **Lint:** the UI's `npm run check` runs eslint with zero warnings on test files too. No `any`: cast with `as unknown as T` where a partial object stands in for a model.
- **The moved `CapturedEmails`/`TestClock` keep their namespace** (`MDBNavigator.API.Tests.Infrastructure`), so `DemoAppFixture` and the demo tests compile unchanged.
- **Release build treats warnings as errors.** Watch for unused `using`s and nullable warnings in the new C# files.

## Changed while building

- **`AppFixture.SampleSchema` uses a four-quote raw string literal.** The new statement `create table "Smoke ""Quoted"""."Mixed Case" ...` contains `"""`, which ends a `"""` raw string early. The literal is now opened and closed with `""""`. The SQL is as in 5.3.
- **`ScriptQuotingTests.ScriptAsync` unwraps a JSON string only on success.** The 404 and 400 answers are JSON error objects (not strings), so `Deserialize<string>` threw on them. The helper now unwraps only when the status is a success and the content type is `application/json`.
- **Every exact string in 5.3 matched PostgreSQL 17's real output**; no expectation needed changing.
